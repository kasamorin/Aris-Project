## 一、可迁移性原则（D14）

**目标定义**：用户从一台主机迁到另一台主机时，只需

1. 在新主机 `git clone` 本项目
2. 把原主机的 **`data/` 目录全量复制**过来
3. `uv run aris serve`

即可直接启动，**不需要**手工改配置、手工建库、手工装 PostgreSQL。

### 硬约束（实现时必须遵守）

| 约束 | 原因 |
|---|---|
| **不得写死绝对路径** | `data/` 可能落在任何位置；DSN/路径一律由 `<data_dir>` 推导（现状已满足：`pgenv.detect()` 把相对路径 resolve 成运行期绝对路径，不入库） |
| **不得把"已验证状态"存进库** | 便携 PG 二进制是否可用、模型是否已下载等，都必须在**启动时重新探测**，不能信任从旧机带来的标记 |
| **启动幂等** | 重复执行 `aris serve` 不得产生副作用；缺什么补什么 |
| **跨平台必须可降级重获取** | 便携 PG 二进制是**平台相关**的（Linux x86_64 ≠ macOS ≠ aarch64）。检测到不兼容时，应走 `bootstrap_env()` **重新获取**（联网）或报可操作错误，而不是直接崩 |

### `data/` 内容分层（迁移清单）

| 类别 | 路径 | 迁移 | 说明 |
|---|---|---|---|
| **必须带** | `data/pgdata/` | ✅ 手动拷 | 数据库数据目录——**记忆/会话/知识库全在这里**，丢了等于失忆 |
| **必须带** | `data/knowledge/` | ✅ 手动拷 | 知识库原始文档（与库内 chunk 对应） |
| **必须带** | `data/characters/` | ✅ 手动拷 | 人格文件（D1 定案的载体） |
| **必须带** | `data/skills/` | ✅ 手动拷 | 用户技能（D7 定案的目标目录） |
| **必须带** | `data/autorun/tasks.toml` | ✅ 手动拷 | 用户任务实例（D11 定案） |
| **必须带** | `data/logs/` | 可选 | 人类可读日志，带不带都不影响启动 |
| **可重建** | `data/pg/`（PG 二进制） | ❌ 建议不拷 | 平台相关；启动探测到不可用/缺失 → 重新 `bootstrap_env()`（需联网数分钟） |
| **可重建** | `data/models/`（HF 模型） | ❌ 建议不拷 | 平台/框架相关，体积大；缺失时按需重新下载（`HF_HOME` 已指向此） |
| **可重建** | `data/.uv-cache` / 各类缓存 | ❌ 不拷 | 纯缓存 |
| **不在此目录** | `.venv/`、`uv.lock` | ❌ | 新机 `uv sync` 重建（`uv.lock` 随仓库） |

### 已知的三个缺口（实现时要处理）

1. **PG 二进制的平台相关**：从旧机带来的 `data/pg/` 可能直接不可执行 →
   启动探针需**实际验证二进制可运行**（不只是文件存在），失败则触发重获取
2. **`pgdata` 属主与 `$USER` 绑定**：现状 `PgEnv.user = $ARIS_PG_USER or $USER or "postgres"`，
   且 DSN 用 `postgresql://{user}@127.0.0.1:{port}/{db}`。换机后用户名不同 →
   **连接会失败**。需要定一种做法：把 PG 角色固定成与主机无关的名字（如统一用 `aris`），
   或启动时用现有角色名探测/对齐
3. **端口可能被占**：`ARIS_PG_PORT` 默认值固定 → 新机该端口被占时启动失败，
   需要探测可用端口或给出清晰错误（现状：探活链已有部分能力，待补）

### 与既有的关系

- `store/` 的探针链（`ARIS_PG_BIN` → PATH → `data/pg/` → 下载）**已经是为这个目标设计的**，
  本条主要是补"跨平台重获取"与"属主/端口"两处
- `aris doctor` 应新增一项「迁移自检」：检查 `data/` 分层完整性 + PG 可运行性

## 二、单一会话原则（D15）

**目标定义**：Aris **只有一个当前会话**（single-session）。**不做、也不允许子代理**
（subagent）——一切输入无论来自哪里，都进入同一个会话，不靠子代理分流。

用户原话立意：**正常人不会让助理代替自己刷社交软件**。

### 会话复用规则

- **复用最新小会话**：无论从哪个通道开始聊天，都直接进同一个 `session_id`
  （不按通道开新会话）
- **冷却上限 = 1 天**（可配，最大 5 天；默认 1 天）：超时才开新小会话。
  拉这么长的理由：**AI API 的 KV cache 磁盘存活期是几小时~几天**，复用同一会话
  能吃到 prompt cache，直接省钱
- **"一段连续对话"是大会话的定义，不是小会话的**——`system prompt → 一轮问答` 即小会话；
  它**跨天存在**，中间的空档由大会话的时间聚类去划分（D2/D3）

### 概念澄清（避免实现走偏）

1. **"不允许子代理" ≠ 禁止一切额外 LLM 调用**：compact 摘要、记忆提取这类
   **为服务主对话而做的一次调用**，是同一会话的**内部维护动作**，不算子代理
2. **autorun 分两类**（与 D11 衔接）：
   - **主动任务类**（如"提醒 Aris 看社交软件"）→ **进当前上下文**，
     但消息需带**系统提示标识**（`kind=system`）
   - **内部维护类**（如夜间整理记忆）→ 走系统内部场合，不污染人类对话
3. **并发输入 = 串行排队**：单一会话是单线程语义；多个来源（TUI / 语音 / SNS）同时来消息
   时**一次处理一个**，靠队列，不并行改变历史

### 场合与去向模型（**当前只写文档，不实现；含独白**）

> **2026-09-28 追加确认：独白（`monologue`）也暂不实现。** 整个"去向"层只留存设计，
> **不写代码**。STT / TTS / SNS 目前也都不存在。此处唯一的作用是：将来做它们时，
> 按这份设计走，不走偏。

**核心洞察**：不是"给会话贴一个渠道标签"，而是**双向的"场合 + 去向"**——
因为对话可能**一对多**（多人/多场合并发），而且**这边语音聊着、那边 SNS 有人发话**必然发生。

#### 入消息：场合（scene）

| 字段 | 取值 | 说明 |
|---|---|---|
| `scene` | `<通道>:<对话方>`，如 `sns:某人` / `voice:Morin` | **场合 = 通道 + 对话方** |
| `channel` | `tui` / `voice` / `sns` / `internal` | 通道（决定"场合风格"） |
| `speaker` | 用户标识 或 `aris` 或 `system` | 一对多必须区分谁在说 |
| `expects_reply` | bool | 该消息是否期待 Aris 回应（SNS 里刷到的不一定要回） |
| `kind` | `human` / `aris` / `aris_monologue` / `system` | 消息性质 |
| `source` | 同上（元数据） | 来源系统，**入库供溯源/审计/WebUI 时间线** |

- **历史是合并的**：不按对话方分独立上下文（那与"单一会话"冲突，且 Aris 会记不住跨人的事）
- 每条消息带说话者与场合，模型据此分辨"谁在哪个场合说了什么"

#### 出消息：去向（target）

**固定枚举，模型声明去向，代码负责分发**：

| `output_target` | 含义 |
|---|---|
| `current` | 回当前场合（默认） |
| `sns:<对话方>` | 发到某个社交场合 |
| `tts` | 走语音输出 |
| `monologue` | **独白/思索**（不对任何人说） |
| `none` | 不发（只想/只记） |

- **独白进历史**（`kind=aris_monologue`）：下次能续上自己的思考，也参与大会话聚类与记忆提取
- **sns 双向都算 sns**：读到别人的社交消息与 Aris 往社交发的回复都标 `sns`，
  口吻判断才一致

#### 场合风格（channel → 风格）

配置里放**渠道 → 场合描述 + 风格要求**的映射（`data/config/chat.toml`），加渠道改配置不改代码：

```toml
[channels.voice]
desc = "语音对话"
style = "回复要口语化、简短、适合朗读；不要列表、代码块、表情符号"

[channels.sns]
desc = "社交平台"
style = "像在社交平台上发言；可以短、口语、带点梗，但不刷屏"

[channels.tui]
desc = "终端调试"
style = "可以稍详细，允许代码块与列表"
```

**注入格式**（只注入"当前场合"，不污染历史）：

```
[当前场合：语音对话] 你正在与 Morin 语音交谈——回复要口语化、简短、适合朗读，不要列表/代码块/表情符号。
```

#### 输出路由为什么不能只做"每轮一个主渠道"

用户指出："万一这边正在语音聊天，那边有人在 sns 发句话"——场景是：
入消息 `{scene: sns:某人, expects_reply: true}` 到达，而 Aris 正在语音场合。
正确行为是**同一段历史里两种去向**：先对 TTS 说"稍等，我看下手机"，再对 SNS 回一句。
因此**去向必须挂在输出上，而不是挂在会话上**。

## 三、对既有设计的修订影响

| 既有设计 | 影响 |
|---|---|
| `WEBUI.md` 会话模型（D2 修订版） | 补：小会话可**跨天**存在（冷却默认 1 天），"一段连续对话"属大会话 |
| `ChatSession`（`cli.py:544` 每次新建） | 改为**取最新小会话续用**；无则新建 |
| `memory_sessions` 表 | 补 `scene` / `channel` / `last_active_at`（冷却判定用） |
| `memory_messages` 表 | 补 `source` / `speaker` / `kind` / `expects_reply` |
| D11 autorun | 补：主动任务类带 `kind=system` 进当前会话；内部维护类走系统场合 |
| `aris doctor` | 补「迁移自检」项 |
| `data/config/chat.toml` | 补 `channels.*`（场合风格）与 `session_cooldown_days` |
