## 1. 总原则（已定，写代码前先认这些）

1. **全量清单**：`todolist.md` 顶部的条目在 v1.0.0 内全部完成（Bug fix 与「以后再说」的除外）。
2. **单人维护**：没有协作者；流程为一个人可执行、可回滚的流程；不引入需要团队协作的机制。
3. **标准流程**：feature 分支 → PR → `develop`；发版走 `release/vX.Y.Z → main` 单 PR；CHANGELOG 规则见 AGENTS §9。
4. **CLI 功能 ≥ 前端**：前端（WebUI / GUI）有的能力 CLI 先有；CLI 与前端共用同一套总线服务。
5. **运行时数据只在 `data/`**：备份只备份 `data/`；`data/` 之外不放运行期状态。
6. **CMCB 是模块间唯一通讯方式**：模块之间不 import；项目内部不加 HTTP 接口。
7. **单一会话 / 每角色一个**：不并行改历史；不做子代理；并发输入串行排队。
8. **CMCB 单进程**：所有模块在同一个进程里，进程内协作靠总线事件（如备份冻结）。
9. **必填配置缺失 = 错误处理**：该功能不可用 + error 日志，不静默取默认值；可选项才用默认值。
10. **不加密密钥**：与 AIRI / opencode / AstrBot / DSH 一致，靠 0600 权限 + 配置只存 key 名 + 展示脱敏。
11. **文档分层**：人类文档在 `docs/` 根；AI 文档只在 `AGENTS.md`（`CLAUDE.md`）与 `docs/forAiDoc/`；
    人类文档不指向 AI 文档。
12. **不做未定的事**：待定项不替开发者决定，列在本文 §7。

## 3. 全局基础设施

### 3.1 数据目录

- 安装态：**`~/.aris-project`**（2026-11-06 已改；此前代码里是 `.project-aris` 的旧名）。
  包安装与源码是两种数据位置：**包安装用 `~/.aris-project`，源码树用项目根下的 `data/`**。
  不上 Flatpak，不做 XDG。
- 解析顺序：`ARIS_DATA_DIR`（进程环境）> 开发树 `./data` > `~/.aris-project`。
- 换机 = clone → 拷 `data/` → `uv run aris serve`。
- `data/` 下必须带：`config/` `pgdata/` `knowledge/` `characters/` `skills/` `autorun/`；
  可重建：`pg/` `bin/` `models/` `logs/` `state/`。

### 3.2 多配置档（cfg profile）

- 每档一个 **cfid**；目录 `data/config/<cfid>/`。
- 默认档 cfid 固定为 **`normalconfig`**：**内容可改**，但 cfid 不变、不可删除。
- 当前档由 **`data/config/active`** 文件决定：无后缀，一行 cfid。
- 首次启动 / 缺失时播种到 `normalconfig`；现有 `data/config/*.toml` 在功能落地时迁移进默认档
  （功能未上线前不动现有 `data/`）。
- 设置页提供「恢复默认设置」（仅内容，不删档）。
- **细节（2026-11-01 定）**：
  - `active`：无后缀单行 cfid + 换行；缺失 → 播种 `normalconfig`；指向不存在的 cfid → 回退
    `normalconfig` + warning；含非法字符 → error + 回退；
  - **切换档**复用设置页那套：能热生效的立即生效，需要重启的走同一个「立即重启 / 稍后重启」弹窗；
  - **监听地址与端口不随档**（2026-11-03 定）：`serve.toml` / `webui.toml` **整体全局**，留在
    `data/config/` 根，不放进 `data/config/<cfid>/`。理由：从别人的备份恢复配置时，若端口随档，
    恢复后 WebUI 链接会打不开；端口属于「这台机器怎么对外」，不是「角色怎么说话」。
    不做新的 `network.toml`——少一份文件、少一处真相。
  - 这里的端口指 **WebUI / serve 的监听端口**；便携 PG 集群端口仍运行期分配、不进配置（AGENTS §可迁移性）。
  - **GUI 不得写死端口**：前端只认后端给出的地址（启动参数 / 环境变量 / 连接信息文件 / 现有地址重定向），
    具体发现方式见 §4.15「后端地址发现」。
  - **新建档 = 以种子默认值新建**（不复制当前档）；
  - **删除**：`normalconfig` 不可删；当前档不可删（先切走）；**删前不自动备份，但要警告**；
  - **重命名**：支持（校验 cfid 合法性，同步 `active`）；
  - CLI：`aris config profile list|use|new|rename|rm`。
- **随档**：`settings / modules / chat / search / decision / logging / audit / notify / store / knowledge /
  multimodal / compact / tools / autorun / memory`。新增文件（`compact.toml`、`tools.toml`、
  `multimodal.toml`、`memory.toml`、`autorun.toml`、`decision.toml`）随对应批次落地，落地即归入这一档清单。
- **全局（不随档）**：`serve.toml`、`webui.toml`、`secrets.toml`、`providers.toml`、`mcp.toml`、
  `platforms.toml`，以及将来「统一连接」页管理的外部提供商配置（理由：换档不应换监听地址、外部连接与密钥；
  统一连接一条配置多档共用；平台账号与白名单属于「这台机器连了谁」）。
- **插件设置**：由插件自己提供与管理，不进核心配置档。

### 3.3 配置项与「设置」

- 术语：后端事实叫**配置项**；前端称呼叫**设置**（设置是配置的前端）。
- **设置页覆盖全部配置项**（2026-11-01 定）：正常情况下用户只用前端就能完成所有正常操作，
  CLI 只在出问题、脚本化、故障救援时用。"CLI ≥ WebUI" 指**能力对等（CLI 不少）**，
  不是"要求用户以 CLI 为主"。
- **设置页结构（2026-11-03 定，取消简单 / 高级两个视图）**：顶部「配置档切换 + 按模块分类 + 搜索」，
  下面**只有一套完整列表**——所有配置项按分类分组、组内再分 `section`，某项只在相关开关打开时出现
  （`condition`）。靠分组与条件显隐控长，不做两套视图（两套要额外维护，还容易「简单视图漏项」）。
- **分类呈现（2026-11-01 定）**：顶部一条**横向可滑动的分类 tab 条**（支持左右拖/滑动、
  触屏滑动、滚轮），下面内容区按分类分组，每组一个标题 + 卡片列表；卡片 = 名称 + 一句简述 + 右侧控件。
- **保存方式（2026-11-01 定）**：页面**左下角保存按钮**，只有存在未保存改动时才出现；
  点击 = 写入 TOML + 重载配置。不做逐项即时保存。离开页面时有未保存改动要提示。
- **生效方式（2026-11-01 定）**：能热生效的保存后**自动生效**；需要重启的保存成功后**弹窗提示**，
  给「立即重启 / 稍后重启」两个选项；选稍后的，在**侧栏底部**保留一个持久提醒（无顶栏，靠它兜底）。
  **2026-11-08 收窄**：只有属主模块真的提供 `reload()` 的项才标 `hot`；其余一律 `restart`，
  不承诺普遍热生效。
- **重启实现（2026-11-01 定，参考 AstrBot）**：优雅停机后 **`os.execv` 原地替换进程**
  （同 PID；`sys.executable -m aris <原参数>`；先停插件 / MCP / 调度器、释放 DB 连接池，
  PG 不停——启动是幂等的）。前端点「立即重启」后显示遮罩「正在重启…」并轮询健康接口，恢复后自动刷新；
  超时给「请手动重启」。
  **GUI 不托管后端**：GUI 只是前端（webview 加载 WebUI），后端可独立运行；因此重启始终由后端
  自己完成，不需要 desktop-managed 守卫。
- **原始键名与所在 toml 文件默认不显示**；由前端状态 `show_raw_keys`（`<data>/state/ui.json`，
  默认 `false`）控制，打开后在每条简述下面加一行 `chat.temperature · chat.toml`。
  它在设置页里就是一个**普通卡片**（「界面」分类），但**不是配置项**——不进 `config.items`、不随配置档、
  也不进元数据表；不放页面顶部（顶部已有配置档、分类、搜索，再加会挤）。

#### 配置项元数据（S1 契约，2026-11-03 定）

- **单一来源**：元数据**贴在 dataclass 字段上**（`Annotated`），默认值就是 dataclass 默认值，
  **不在别处再抄一份**。对比 AstrBot 的 `CONFIG_METADATA` + `DEFAULT_CONFIG` 两棵树——它要渲染任意嵌套
  结构，多一份默认值值得；我们已把结构化配置分出去（走专用页面），不需要为嵌套付漂移成本。
- 声明形态：

```python
from typing import Annotated

from aris.infra.config_items import Item


@dataclass
class SearchConfig:
    results_count: Annotated[int, Item(section="search", min=1, max=20)] = 5
    timeout_seconds: Annotated[float, Item(section="search", min=1.0, max=120.0, step=0.5)] = 15.0
```

- 字段表（`—` = 自动推导）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `key` | 自动 | `<toml 主名>.<字段名>`（嵌套表加前缀）；CLI / 前端 / 审计共用这一个 id |
| `file` / `scope` | 自动 | 由「dataclass ↔ 文件」注册表给出；`scope` **按文件**定（profile / global，见 §3.2） |
| `type` / `default` / `choices` | 自动 | 类型从注解推；注解是 `StrEnum` 就直接出下拉 |
| `label` / `desc` | 自动 key | `config.<key>.label` / `.desc`；文案进 `locales/`，代码里不写中文 |
| `category` / `section` | 见 §3.3.1 / — | `category` 是分类 tab（默认取文件→tab 映射），`section` 是 tab 内的小标题 |
| `control` | 自动 | `text / textarea / number / switch / select / path / color`，可手写覆盖 |
| `apply` | `restart` | `hot` 仅在**属主模块提供 `reload()`** 时允许，否则一律 `restart` |
| `required` | `false` | 留空即错误（走上面的「必填留空」流程） |
| `auto_empty` | `false` | 留空 = auto（请求里不传该字段） |
| `secret` | `false` | 前端脱敏显示 |
| `hidden` | `false` | 不进设置页，CLI 仍可见 |
| `min` / `max` / `step` / `pattern` | — | 数值 / 字符串校验 + 控件参数 |
| `condition` | — | `{同文件另一个键: 期望值}`，不满足则整项不渲染（借 AstrBot） |
| `section_condition` | — | 段级条件，形状同 `condition`；不满足则**整个 section 不渲染**。同段字段取值必须一致，一致性由测试校验（借 AstrBot 的 `dify_runner` 式条件段） |
| `collapsed` | `false` | 所在 `section` 默认折叠（同 section 取「或」）；只影响展示，不影响取值。**按冷门程度用，不按长度用**（§3.3.2） |

- **两条自动检查**（防漂移）：每条 item 都有 `label` / `desc` 译文，缺了测试失败；
  `config.items` 返回的条目与 dataclass 字段**一一对应**，多写少写都失败。
- **输出**：**不提供 `aris config items` CLI**（2026-11-07 定）；全量元数据只经 `config.items`
  总线服务给设置页，CLI 侧保留 `config path/list/show/validate`；前端走 `config.items`
  + `/api/config/items`，只消费、不自己定义字段。
  **返回形状（2026-11-08 定）**：**扁平 `list[dict]`**，每项带
  `key / file / scope / module / module_enabled / category / section / type / default /
  control / apply / required / auto_empty / secret / hidden / nullable / choices /
  min / max / step / pattern / options / collapsed / condition`；前端按 `category → section`
  自己分组。不做后端嵌套树：分组映射已在 `CATEGORY_MAP`，再包一层只会多一套要同步的结构。
- **注册副作用**：可关模块的 `__init__` 不 `provide()` / 不 import 迁移，改由 `serve.assemble()`
  调用 `register()`；`load_all()` 只 import `<module>/conf.py`（2026-11-07 定，详见 S1 文档 T1）。
- **写回**：设置页用 **`tomlkit`** 只改对应键，**保留注释与格式**；CLI **不新增写命令**
  （改配置用编辑器，`aris config` 维持只读）。
- **不进通用设置页的**：`providers.toml` / `mcp.toml` / `modules.toml` / `search_engines.toml` /
  `platforms.toml` 这类数组 / 表结构走专用页面（提供商管理、统一连接、MCP 管理、模块开关、搜索顺序、
  消息平台）；通用设置页只覆盖**扁平键值** toml。
- **少数前端状态不是配置项**：主题色、`show_raw_keys`、日志滚动位置等直接读写
  `<data>/state/ui.json`，由设置页的普通卡片承载（与配置项同一套外观），但不进 `config.items`、
  不随配置档。
- 前端**不提供**直接编辑 TOML；要手改时用编辑器（这是出问题时的通道，不是日常路径）。
- **危险 / 结构性操作**（重建向量、切换记忆库后端、迁移数据、恢复备份）不属于"配置项"，
  但前端同样必须有入口（带二次确认与影响说明），不能只藏在 CLI 里。
- 字段语义：
  - 有 `auto` 的字段：留空 = auto（请求中不传该字段，交给服务商决定），默认值以灰字提示；
  - 允许留空的字段：留空合法，不强制 auto；
  - 必填字段留空：保存被阻止，输入框红边 + 红字提示；
  - 直接改配置文件留空：加载时记 error、程序不退出；进入前端弹窗提示，关闭后跳设置页并标红（非编辑态）；
  - 用户执意留空：模块用到该配置时**进入错误处理**（功能不可用 + error 日志），不静默取默认值。
- 「更多配置项」的判定标准：**用户真正会改、且改了不会搞坏内部实现**的才进配置；
  代码枚举、协议细节、内置 UA、接口地址、运行时状态等继续留在代码常量里。

#### 分类 tab：文件 → tab 的映射（2026-11-06 定）

#### section 划分（2026-11-06 定）

- 搜索**不做「只过滤列表」**：必须能跳过去（参考 airi 的 `?setting=` + 高亮、Maibot 的跨 tab 导航）。

- 搜索匹配 `label` / `desc` / 原始键名（后者仅在用户开了 `show_raw_keys` 时）。

### 3.4 备份与恢复

**备份**

- 对象只有 `data/`；包 = `tar` + 元信息（manifest）。
- 格式：默认 **`.tar.zst`（zstd -3）**；兜底 `.tar.gz`；恢复同时支持两种。
- 默认**排除可重建内容** `pg/` `bin/` `models/`；前端开关「包含可重建内容」、CLI `--full` 才全量；
  manifest 记录是否 full，恢复时提示「可重建内容已排除，首次启动会自动重新获取」。
- 冻结：CMCB 事件 `system.freeze` / `system.thaw`；`emit` 同步执行，天然充当屏障。
- 安全停库（停服备份，**仅便携实例**；外部 PG 见下面「外部 PostgreSQL」）：
  1. freeze：各模块进入 drain，不再接新任务，**当前任务必须跑完**（如一批 embedding 的当前 chunk）；
  2. 等待所有写模块完成（进度条：从左往右扫的「不确定进度」+ 阶段文字「正在等待安全停止…」）；
  3. 关闭连接池 → `pg_ctl stop -m fast`；
  4. 流式 `tar -C <data>/ . | zstd -3 -T0`；
  5. `pg_ctl start` → 重建连接池 → `thaw`；
  6. 写 manifest、清理临时文件、报告路径与耗时。
- 超时（如 60 秒）→ 中止备份、解冻、报错，不静默强杀；停库或打包失败 → 回滚到「启动 PG + 解冻」。
- 触发入口：应用内（WebUI / GUI）可冻结；CLI 在应用未运行时直接打包（无需冻结）。
  **不引入 HTTP / 跨进程信号**；应用在跑时 CLI 提示改用应用内备份或先停应用（可加 `--force` 明确告知风险）。

**恢复**

- **完全覆盖**，不做增量（`pgdata` 与配置目录无法安全 merge）。
- 应用与 PG 必须已停止，运行中拒绝恢复。
- 恢复前自动打一份「恢复前快照」。
- 校验 manifest（版本字段、cfid、时间、用户备注、格式、是否 full）；**各版本字段的判定规则统一在 §4.19**，
  本节只负责校验动作本身。
- 警告：前端两次确认；CLI 输入 `y` 回车，`-y` 跳过交互。
- 目标路径按 `paths.py` 解析出的 `<data>/`，不硬编码。
- 不做备份包加密；manifest 不额外标注密钥（密钥就在 `secrets.toml` 里）。

**存放与清单（2026-11-01 定）**

- 位置：**`<data>/backups/`**——用 `paths` 解析出的数据目录拼，**不写死 `data/`**（数据目录可自定义，
  这是既有规则）；打包时自动排除该目录；可配 `backup_dir`。查证：Home Assistant、Immich、Gitea
  都把备份放在应用数据目录内并用界面管理；坏处是同盘不防盘坏，页面上要写明。
- 命名：`<app_version>-<YYYYMMDDTHHMMSSZ>-<cfid>.tar.zst`，旁车 `<同名>.sha256`。
- **不自动删除**（用户定）；页面显示占用大小，删除由用户手动操作。
- `manifest.json` 放归档根：`format_version` / `created_at` / `app_version` / `db_schema_version` /
  `platform`+`arch` / `cfid` / `full`+`excluded` / `compression` / `file_count`+`total_bytes` /
  `notes` / `contains_secrets` / `payload_sha256`。**不记录主机名**（隐私）。
- 超时：drain 60 s、`pg_ctl stop` 30 s、打包/解包无总超时但 **60 s 无进展判卡死**；超时一律中止并回滚。
- 恢复后**自检**：起 PG、`SELECT 1`、关键表存在、全部 TOML 可解析、`active` 指向存在的 cfid；
  失败自动回滚到"恢复前快照"。
- **WebUI 全流程**：列表（时间 / 大小 / 版本 / 是否 full / 备注）、新建（含 full 开关）、恢复（两次确认）、
  下载、删除；恢复完成后的**重载复用设置页那套机制**（重载配置 + 重启相关模块）。
- **跨版本恢复**：见 §4.19——新版本必须能恢复旧版本备份，除非在发布说明里明确声明最低兼容版本。

**外部 PostgreSQL（2026-11-03 定）**

- **结论：保留外部 PG 支持**。查证：Dify（`DB_HOST` / `DB_PORT`）、n8n（`DB_POSTGRESDB_HOST`）、
  RAGFlow（`POSTGRES_HOST` / `POSTGRES_PORT`）、Immich（`DB_HOSTNAME` / `DB_URL`）都允许指向外部实例
  ——这是自托管产品的通行做法。
- **绝不停、不打包别人的库**：外部 PG 下**不执行** `pg_ctl stop`、不碰对方的 `data/` 目录、不假设能停服。
- **备份改用逻辑导出**：`pg_dump -Fc` 导出到包根的 `db.dump`，manifest 记 `db_backup: pg_dump` +
  服务端主版本 + `pg_dump` 主版本；恢复走 `pg_restore --clean --if-exists` 到用户确认的目标库。
- **版本前提**：`pg_dump` 主版本必须 **≥ 服务端**；优先用用户配置的 PG 二进制目录（`ARIS_PG_BIN`，
  或外部实例自带的 bin）。拿不到匹配版本 → 退化为「不备份数据库」：manifest 记 `db_backup: none`，
  备份前后端与 CLI 都明确提示「数据库未备份，请自行处理」，**不静默放过**。
- 冻结 / 解冻（`system.freeze` / `system.thaw`）对两种实例都照常做，只跳过停库与打包 `pgdata/`。
- 恢复后自检：`SELECT 1` + 关键表存在 + 配置可解析；外部实例不做「起库 / 回滚快照」。

### 3.5 能力注册表与统一连接

整套可扩展能力用同一套模型：

```
能力域 = 注册表 + 条目
条目   = { id, 来源(内置|API|MCP|插件), 协议类型, 配置字段, 启用态, 可删除性 }   # 插件来源 v1.1 才出现
能力域 = { 是否有序（故障降级 / 优先级）, 顺序配置, 是否允许新建/删除 }
```

- 适用：搜索引擎、LLM 提供商、TTS、STT、embedding；**消息平台先不套用**（形态不同，单独设计）。
- 顺序列表只表达**故障降级顺序与优先级**，**不做竞速**；LLM 的降级链单独由 `providers.toml`
  顶层 `fallback_models` 定义（§3.9），不按提供方顺序降级。顶部输入框 + 可拖动列表双向同步；
  新条目默认追加到末尾。
- 统一连接页：LLM / MCP / 搜索 / TTS / STT / embedding 的**对外连接**集中在一个页面配置（全局，不随档）。
- 条目来源与可删除性规则见各功能域章节。

### 3.6 错误处理

- 必填配置缺失/非法 → 功能不可用 + error 日志；不退出程序。
- CMCB `call` 返回 `None`（服务不可用）时要显式处理，不能直接属性访问。
- 降级必须记日志，禁止静默失败。

### 3.7 存储总线化（2026-11-06 定走方案 A）

- **目标**：业务模块不再直接 import `store` 的实现，一律经 CMCB（`store.*` 服务）。
  `store` 目前是基础设施里唯一「被直接 import 而非经总线」的大件，v1 内收掉。
- **为什么放 S5（存储适配）**：S5 本来就要改连接方式、embedding 后端与「库绑定 embedding」，
  总线化顺手做；分两次改同一片代码等于返工。
- **已定方案 A（池化上下文，2026-11-06）**：
  - `store.connect` 从「每次新建裸连接」改为**从连接池借、用完归还**
    （`psycopg_pool.ConnectionPool`，新增依赖 `psycopg[pool]`）；池在 store 内部建，
    **pgvector 适配器在池的 `configure` 回调里统一注册**；
  - 调用方写法不变：`with call_required("store.connect") as conn, conn.transaction():`；
    **事务边界仍归调用方**——只有它知道哪几条 SQL 必须原子；
  - 池化是为了解决现在没有连接池、每条连接都完整握手的问题；**不是为了藏 SQL**；
  - 备份流程里的「关闭连接池 → 停库 / 重建连接池 → 解冻」按现在的 §3.4 不变；
    psycopg 池会自动剔除死连接，外部 PG 重启后不必手动干预。
- **不走连接池**：`memory-lite`（SQLite stdlib），没有池概念，和 full 分开。
- **保留的直接引用**（AGENTS §6「不走总线的边界」）：纯类型 / 契约引用。
  例如 knowledge 的迁移登记（`Migration` / `register`）属于启动期装配，不走总线。
- **出口条件**：业务模块里只剩类型引用；`store.*` 服务覆盖业务真正需要的动作
  （连接、迁移登记、向量读写、embedding、健康）；**调用方不再自己 close、也不做每次握手**。
- **S5 内定的两个细节**：① 是否新增 `call_required()`（缺服务直接抛 `ServiceMissing`；
  `call` 保持返回 `None`，不惊动全仓调用点）；② `store.toml` 的池参数（建议
  `pool_min=1` / `pool_max=8` / `pool_timeout=30`）。

### 3.8 外部组件清单（2026-11-06 定）

**一句话**：所有要下载到 `data/` 的第三方产物的**来源、版本、校验值**集中写在
`src/aris/infra/components.py` 的常量里；升级 = 改这个文件 + 发版，不再散落在各模块。

- **位置与格式（2026-11-06 定）**：`src/aris/infra/components.py`，**Python 常量**
  （dataclass / TypedDict）。选 py 不选 TOML：随代码走、有类型与 IDE 补全、不需要额外的资源打包
  与解析层；`infra` 里 `settings.py` / `paths.py` 已经是「事实放代码里」的同款做法。
- **收录范围（2026-11-07 修订）**：v1 只收**运行期真的要获取到 `data/` 的东西**——
  便携 PG、pgvector、micromamba（PG 的引导器）、embedding 模型。
  **uv 不收**：它是打包时的构建工具（deb 里随包分发），运行期一次都不用；收了会让清单从
  「运行时要下载什么」变成「项目用过哪些工具」，没有边界。uv 版本钉在 S13 打包脚本里。
  STT / TTS / 本地推理运行时**等真正引入时再加**，v1 不预留空结构（YAGNI）。
- **不是配置**：不进 `data/config/`、不进设置页、不随配置档。
  它是「我们测过并承诺支持的那一组版本」，属于**代码事实**，不是可调项。
- **用户覆盖来源（2026-11-07 修订）**：**不新增 `components.toml`**；镜像写进现有
  `data/config/store.toml` 的 `[mirror]`，**只允许覆盖 `url`**（镜像 / 代理地址），
  `sha256` **永远来自 `components.py`**。键的两种写法（见 `resolve_url` 的 docstring）：
  `"<id>"` = 镜像目录（自动拼官方文件名）、`"<id>.<platform>"` = 完整 URL 精确覆盖。
  镜像必须是**字节一致的副本**，否则校验失败——用户绕不过校验，只是换了个下载地址。
  要换版本 / 换产物只能改代码发版；用户不改代码。
- **缺校验即失败**：每个可下载条目必须带 `sha256`；缺失或对不上时**中止并报错**，
  不允许「跳过校验继续装」。
- **收编现状**（此前散在模块常量里）：

  | 现在的位置 | 内容 |
  |---|---|
  | `store/bootstrap.py` | `MAMBA_VERSION` / `MAMBA_URL` / `MAMBA_SHA256` / `PG_VERSION` / `PGVECTOR_SPEC` / `CONDA_CHANNEL` |
  | `store/embedding/local.py` | `DEFAULT_MODEL` / `BEKKO_A25M_DIM`；加载读 `refs/main`（浮动，收编时一并锁 revision） |
  | `store/conf.py` | `local_model` 默认值 |

- **三种条目，不硬塞一个 dataclass**：`Archive`（下载文件，必须逐平台 sha256）、
  `CondaPackage`（精确版本 + channel，完整性由 conda repodata 负责）、
  `Model`（HF 仓库 + commit + 维度）。平台归一（`linux-64` / `linux-aarch64`）只在 `components.py` 做。

- **为什么值得单独一处**：
  - 一处改、一处审：升级外部组件不再靠全仓搜常量；
  - **来源与版本解耦**：以后从 micromamba + conda 换成我们自建产物（§7-29），
    只改 URL / 去掉 channel，不动业务代码；
  - CI 可以拿它做守门测试（链接还活着、sha256 还对、与文档版本一致），
    而不是等用户首次启动失败才发现。
- **配套**：`aris components list`（只读）打印清单（组件 / 版本 / 来源 / 校验值），
  与 `aris info` 同属「事实用 CLI 表达」。
- **版本语义**：embedding 模型用 **HF revision（commit）** 锁，不跟 floating tag
  （`main` 随时会变，锁 tag 也不够）；`LocalBekkoProvider` 加载时传 `revision`，
  缓存里只有别的 commit 时**不拿它顶替**（否则锁 revision 失效）。
  **PG / pgvector / micromamba 一律精确钉死具体版本**，不写 `>=`；升级 = 改 `components.py` + 发版。
  当前钉 `postgresql=17` / `pgvector=0.8.1` / `micromamba=2.9.0-0`（与现有 `data/pgdata` 一致）；
  §7-29 定下的目标 `18.6 / 0.8.6` 在 S5 连同 `data/pgdata` 重建一起切换。

**本节待定**：无（覆盖方式已定，见上）。

### 3.9 core 优化范围（2026-11-08 定）

已定进 v1，只动三块，不做全量重写：

1. **LLM 引擎拆分 + fallback 重写**：`core/llm/engine.py` 拆成「流式消费 / 故障处理 / 重试与降级」
   三块，收出 provider 边界，并按下面的新口径**推翻现有三层**。
2. **工具循环可控性**：工具执行中可中断、每工具统一超时、结果截断与错误归一
   （现在超时与异常都靠工具自己处理）。
3. **工具循环并行调用**：模型一次返回多个 `tool_call` 时，按工具声明的「并发安全」标记决定
   并行 / 串行；**写类工具默认串行**，副作用顺序必须可预期。

**fallback 口径（2026-11-08 定，推翻现有三层）**

- **默认模型必须显式配置**：`providers.toml` 顶层 `default_model`；缺失 / 无效按**配置错误**处理
  （启动清单与 `aris doctor` 报错，功能不可用），不再静默取第一个可用模型。
- **全局一条 fallback 链**：`providers.toml` 顶层 `fallback_models = [...]`，有序；**没有**
  每模型自带链，也**没有**「同模型换提供方」的横向链。一个模型 id 只能属于一个提供方，
  重复即配置错误（旧 `fallback_models` 字段在 S7 退役）。
- **请求流程**：
  1. 用默认模型请求（会话显式切换过的模型，失败后同样走下面的链）；
  2. 出错 → **立即发出 `settings.llm_error_message` 占位**，消息平台与 WebChat 一致；
  3. **同模型、同提供方重试一次**；
  4. 仍失败 → 按全局 fallback 链逐个模型尝试，直到成功；
  5. 链走完仍失败 / 根本没配链 → **停在占位，等下一次请求**；下一次仍从默认模型开始。
- **不粘滞**：本次 fallback 成功不改变下一次请求的起点，也不在会话里记「降级中」。
- **不做竞速**：删掉 `stream_deltas_race` 与降级后竞速恢复（AstrBot / opencode / AIRI 都不做）。
- **已输出内容后不切换**：一旦流过真实内容或执行过工具，失败就直接进错误处理，不再重试 / 降级，
  避免重复文本与重复工具副作用（三家一致）。
- 占位**保留**：fallback 成功后的回答接在占位后面，WebChat 也不替换 / 撤回，保持与消息平台一致。
- **S7 落地时同步更新** `docs/forAiDoc/LLM-PROVIDER-MGMT.md` 的 `default_model` / fallback 段：
  现在那份契约还写着「缺失即取 order 第一个模型」，与新口径冲突，别让文档停在旧行为。

**硬约束（中断）**：工具执行中途被中断时，**必须为每个已发出的 `tool_call` 补一条 `tool` 消息**
（内容如「已中断」），再结束本轮；否则下一轮请求会因 `tool_call` 缺少对应 `tool` 结果被
OpenAI 兼容提供方拒绝，DeepSeek 的工具调用约束同理（`reasoning_content` 回传 + `tool_call` 配对），
不能只回滚 user 消息了事。

  - `webui/`：前端源码（Tailwind 入口 CSS、daisyUI 主题、桌面适配层），自己的 package.json + lock；

### 4.2 LLM 连接与提供商重构

- **完全重构** provider 层：按 API 格式适配（OpenAI Chat Completions / OpenAI Responses / Anthropic /
  其他官方适配），官方支持一批需要专门适配的提供商。
- **模型列表**：
  - 按创建提供商时选的 API 格式决定如何获取 `/models`；
  - 返回里带上下文长度 / 模态等元信息就直接展示；没有就给用户手动编辑
    （是否支持思考 / 工具 / 图形理解 / 语音）并允许手动增删；
  - **允许模型列表**（持久化）与**联网获取列表**（不持久化）分开；「+」把模型加入允许列表并从联网列表
    视觉上隐藏（实际只是加入允许列表）；再次获取时仍按允许列表过滤；
  - fallback 只用允许列表，避免联网列表里的模型意外产生费用。
- **fallback 策略（2026-11-08 重定，覆盖旧 D9）**：以 **§3.9「fallback 口径」**为准——
  默认模型必配；出错先发占位 → 同模型同提供方重试一次 → **全局一条** fallback 链逐个尝试 →
  全失败 / 无链就停在占位等下一次请求；不粘滞、不竞速。
  - **没有**「同模型跨提供方切换」，**没有**每模型 `fallback_models`；一个模型 id 只属于一个提供方。
  - fallback 链只能从**允许模型列表**里选，避免联网列表里的模型意外产生费用。
  - **关闭 SDK 内建重试**（`max_retries=0`），重试只由 engine 负责，消除双层重试。
  - **空输出重试**：只回 reasoning、无 content 或空响应时，同模型重试 1 次，**不计入 fallback**。
  - `free` 模型元信息保留，但不再参与 fallback 优先级。
- **手动切换（2026-11-01 定，参考 AstrBot `/provider`；随时可用）**：
  - WebChat：输入框底部下拉，只列**允许模型列表**，显示当前模型；切换**只影响当前会话**，可一键设回全局默认；
  - 消息平台：`/#provider` 列出（当前、序号、可达性 ✅/❌）并 `/#provider <序号>` 切换，同样会话级持久化；
  - 全局默认模型在设置页配置，新会话继承；只有管理员（`admins_id` / `aris_frontend_id`）能切。
- **模型列表只增不自动删**：`/models` 没返回、但实际可请求的模型必须能手动保留，不做「以接口返回为准自动清理」。
- **能力测试**：单模型测 + 该提供商允许模型一键全测；探测文本（PONG 探针）、图片（极小图）、工具（假工具 ping）；
  **实测到的上下文长度等真实值写回允许模型列表的元信息**。
- **取消 models.dev**：元信息改由提供商接口直接提供；缺失时显示「未知」并允许手填，不阻塞。
- 提供商配置全局（不随档）；密钥只在 `secrets.toml`；`providers.toml` 只写 key 名。
- 统一连接页承载 base_url / key 名 / 超时 / transport / 官方预设。

### 4.3 多模态

- **输入与输出都做适配**（不是所有模型全模态）。
- 支持语音输入 + 语音输出的模型：允许**整体替代 STT/TTS**；
  只支持单侧的：允许替代单侧；STT/TTS 链路仍保留。最终选择权给用户。
- 消息模型要支持内容块（文本 / 图片 / 音频等），会影响会话落库、WebChat 渲染、记忆存储；
  所以本域要在记忆落库之前完成消息模型定型。
- 提供商能力（视觉 / 音频 / 工具 / 思考）由模型元信息或用户手填决定——**能力表不在本节重复定义**，
  字段与来源见 §4.2「模型列表」（含 `图形理解` 标记）。

**图片发送投影（2026-11-03 定，AstrBot 同思路）**

- 消息里的图片**始终原样落库**（内容块 + `data/` 文件）；发送给模型只是**投影**，不改历史。
- 投影规则按当前模型的 `图形理解` 能力：
  - **支持** → 原生内容块发图；
  - **不支持** → 若开了「图片转述」→ 先转成文字描述再发；否则换成占位文本（如 `[图片]`），界面提示「当前模型看不到图」。
- **图片转述**（`multimodal.toml`，**随档**）：`image_caption.enabled`（**默认关**）、`provider` / `model`
  （指定一个视觉模型，可与主模型同一个连接）、`prompt`（可改，默认中文描述）；
  转述结果按**图片内容 hash 缓存**，同一张图只转一次；转述失败 → 退回占位 + 记日志，不阻断对话。
- **发送前预处理**（照 AstrBot，默认值可配）：最长边 **1280**（不放大）、编码后**严格小于 512 KiB**、
  自动修正方向、含透明通道用 PNG、GIF / 动图均匀抽 **9 帧拼 3×3**；重新编码时剥掉无用元数据。
  原始文件不动，预处理只生成发送用的预览。

**全模态范围（2026-11-08 定）**

- **v1 不做视频内容块、不做实时视频 / 实时双工**；内容块保留 `type` 扩展位，v1.x 再评估。
- **音频做**：语音输入 / 输出作为内容块与能力适配的一部分，允许模型整体或单侧替代 STT/TTS（见本节开头）。
  这也是「全模态」在 v1 的实际落点——**音频侧部分替代语音链路，视频侧不做**。



### 4.4 消息平台

- 先做 **OneBot v11**；平台抽象层保留（后续 Matrix / Discord 等）。
- 多账号支持在设计内；所有输入进入该角色的**同一会话**，串行排队（不并行改历史）。
- 平台连接配置**全局、不随档**，走**消息平台专用页**（不进「统一连接」页，也不进通用设置页）；
  消息平台 UI 不套用通用能力注册表。
- **角色 ↔ 平台实例（2026-11-03 定，多角色的关键）**：
  - 一个角色**可以绑多个实例**（如 QQ + Discord），但**同一个实例只能属于一个角色**——
    「同一个平台」指**同一个实例**，同一协议类型下开了多个（如两个 OneBot v11 账号）算不同实例，可以分给不同角色；
  - 将来可能放宽成「不同角色共用一个实例」（需共享会话，类似群聊），v1.x 再议（§4.22）；
  - 入站消息的路由因此变成确定的：**平台实例 → 角色（cid）→ 该角色的唯一会话**，不需要猜；
  - 未绑定任何实例的角色不会收到平台消息，但**仍可从前端（WebUI / GUI / CLI）对话**；
  - 前端**不受**这个排他限制：前端是管理视图，选中哪个角色就跟哪个角色说话；
  - **群聊（多个角色进同一个群）与排他规则冲突**，v1.x 单独设计（§4.22）；v1 不做。

**实现口径（2026-11-01 定，参考 AstrBot）**

- **接入方向**：**反向 WebSocket**（我们起 WS server，OneBot v11 实现连进来）+ **HTTP API 出站**；
  默认只监听 `127.0.0.1`、强制 token；正向 WS 不做。与 AstrBot 的 aiocqhttp 同一条路。
- **对接的实现**：主测 **NapCat** 与 **SnowLuma**（较新的 TypeScript QQ→OneBot v11 运行时，提供
  WS 服务端/客户端、HTTP 上报、多账号与 WebUI；自带 MCP 入口，将来可作为 MCP 路径评估）。
  注意：SnowLuma 是 **源码可见 + 非商业许可**（不是开源），我们**只通过 OneBot 协议连接、不复制其代码**；
  它依赖本机 QQ NT 客户端（Windows / Linux / Docker）。
- **OneBot v11 协议要点（已核对官方文档）**：反向 WS 有三种客户端角色（API / Event / Universal，
  Universal 在一条连接上兼做两件事）；握手头带 `X-Self-ID`（机器人 QQ 号）与 `X-Client-Role`，
  鉴权用 access token（`Authorization: Bearer`）；消息段支持 array 格式与 CQ 码两种；事件分 message /
  notice / request / meta_event（heartbeat），API 调用用 `echo` 配对、返回 `retcode`；发送目标要区分
  群 / 私聊 / 临时会话。
- **NapCat**：跨平台（Windows / Linux / macOS x64）、无头、内存约 50–100 MB、Core/Adapter 架构、
  自带网页配置；它自己的 README 反过来推荐 SnowLuma 作为更新更好用的实现，所以我们两个都测。
- **多账号**：全局配置**支持同一平台多个账号**（如两个 OneBot 连接），每个账号有 id、名称、开关、状态；
  连接状态实时显示，失败记日志。消息平台页面：卡片网格（图标 + 状态 + 名称 + 设置 + 开关）+ 顶部
  「刷新 / 新建」（草图见 `docs/process/assets/webui-2026-11-01/message-platforms.jpg`）。
- **单会话与上下文**（关键差异：AstrBot 是**按聊天**分区会话、AIRI 也是多会话；我们是**单会话**）：
  - 所有平台消息进同一会话，**上下文里不放 chat_id / 平台内部 id**（随机串会破坏提示稳定性、
    吃不到 KV cache），只放人类可读的来源标签（如「QQ 群·xxx | 昵称」）；
  - **回复目标见下面的「发送工具」**：普通回复默认回本轮来源；要去别的聊天才调用工具。
  - 自己发出的消息进历史并标记来源，防止把自己当别人；`message_id` 去重防重连重发。

- **发送工具 `send_message`（2026-11-11 定）**：
  - **定位**：普通回复仍然**直出、走流式**（语音链路靠它）；这个工具只补「**不在当前来源说话**」的出口。
  - **自主性（硬原则）**：只要目标在**白名单**内（私聊、群聊都算），角色**想给谁发就给谁发**，
    **不按发送者身份设闸门**。白名单是它生活的**世界边界**，边界之内它有自己的判断——
    它是赛博生命体，不是「主人授权才能开口」的助手。这条是项目定位的直接推论，不因安全顾虑收紧。
  - **参数**：`target`（人类可读别名）+ `text`。**省略 `target` = 沿用本轮上一次发送的目标；
    本轮还没发过 = 本轮来源**。
  - **目标解析**：别名 → 内部 id 由平台层解析；解析失败**返回错误并列出候选别名**；
    内部 id 不进上下文、不进工具签名。别名规则：`平台短名·名称`（如 `QQ群·摸鱼群`），
    重名时补群号 / QQ 号（如 `QQ群·摸鱼群（123456789）`）——稳定、人类可读，不是随机串。
  - **目标范围**：只认**白名单内、已知的聊天**（别名由平台层维护，重启后随入站消息重建）；
    白名单外的目标一律拒绝。
  - **上限**：每轮最多 3 条、同一目标 1 秒 1 条。这是**防工具循环失控**的工程护栏，不是行为约束。
  - **失败**：错误字符串回给模型；发送超时标「结果未知，不要重试」；日志 / 堆栈绝不进聊天。
  - **去重**：工具已把同样的纯文本发到当前来源时，最终答复不再重复发送。
  - **历史**：工具发出的消息追加为 assistant 条目并标目标（如 `[→ QQ群·B] 正文`），
    否则单会话里模型会忘了自己说过什么。
  - **审计**：每次跨目标发送记一条（目标 / 触发来源 / 长度），供主人事后查看——只观察，不拦截。
  - v1 只发文本；媒体与语音留 v1.x（语音另有 TTS 队列）。
- **借鉴 AstrBot 的交互能力**（挑有用的）：唤醒前缀、@ / 回复触发、白名单、忽略自己消息、忽略 @全体、
  回复前缀、回复带 @ / 引用、限流、内容安全检查、消息段（文本 / 图片 / @ / 引用）转换、
  断线自动重连。
- **聊天管理命令**：前缀用 **`/#`**（与 AstrBot 的 `/` 区分）；v1 计划 `/#help`、`/#reset`、
  `/#stop`、`/#stats`、`/#provider`、`/#sid`、`/#name`；`/#new`（compact）与 `/#new-s`（强制新会话）
  **v1 仅管理员**。
  命令在平台侧拦截，不进 LLM。
- **管理员（仿 AstrBot）**：设置里维护 `admins_id` 列表（某消息平台某账户的 id）；WebUI / GUI 的管理员
  id 固定为 **`aris_frontend_id`**；命中即授予 admin 角色（可跑管理员命令、可改高危项）。
- **`/#new` 语义（2026-11-01 定）**：不是清空会话，而是**主动触发一次 compact**（与上下文满时同一套流程：
  先事件总结写记忆、再做 compact 摘要），用于上下文没满但想主动换一段的情况。
- **回复门控档位（参考 AstrBot active_reply）**：
  - 私聊默认全回；群聊默认「@我 / 回复我 / `/#` 前缀」才回；
  - 每个聊天可单独设模式：仅触发（默认）/ **概率回复**（0~1，可配白名单）/ **决策模型门控** / 全回；
  - 概率回复与白名单照 AstrBot 的 `active_reply` 思路；决策模型档是我们新增的低成本门控（见 §4.12）；
  - 群内全量消息持久化 + 工具查询（AstrBot 的 group_message_history）v1 **不做**：只有进会话的消息才入库，
    避免存储爆炸。
- **媒体**：v1 文本 + 图片（下载进 `data/`，走多模态）；语音后置；**长回复转图（t2i）不做**。
- **白名单（v1.0 做，2026-11-01 定）**：总开关 + 按平台勾选 + 允许清单（OneBot v11 即 QQ 号 / 群号）；
  **白名单外的消息一律不进上下文**（也不入历史、不入记忆）；默认**关闭**（个人自用、只监听 127.0.0.1），
  首次接入时提示建议开启。
- **平台配置结构（2026-11-11 定）**：`data/config/platforms.toml`（全局、不随档）一个文件装两样东西——
  `[[accounts]]` 账号（连接参数 + 白名单 + 按聊天类型的门控默认）与顶层**平铺**的 `[[chats]]`（按聊天覆盖）：

  ```toml
  [[accounts]]
  id = "qq-main"
  type = "onebot11"
  name = "主 QQ"
  enabled = true
  # 连接参数...

  [accounts.whitelist]
  enabled = true
  allow = ["12345678", "87654321"]   # 私聊号 / 群号混排；白名单关闭时不生效

  [accounts.gate_defaults]           # 按聊天类型的默认
  private = "always"
  group = "only_trigger"
  probability = 0.3                  # 概率档 / 决策降级用的回复概率

  [[chats]]                          # 只写覆盖；没列的走 gate_defaults.<type>
  account = "qq-main"
  id = "87654321"
  type = "group"                     # group | private
  name = "摸鱼群"                     # 仅手改识别用，显示以运行时别名为准
  gate = "decision_batch"
  probability = 0.5                  # 可选，缺省用 gate_defaults.probability
  ```

  - **为什么平铺不嵌套**：`[[accounts.chats]]` 在 TOML 里绑定「最后一个 `[[accounts]]`」，位置敏感、
    手改容易挂错账号；平铺数组用 `account` 指归属，没有这个陷阱。
  - **白名单与门控同处一文**：它们是同一件事的两面（谁进得来 / 进来后怎么对待），且都按账号落地；
    拆成两份存储会让人找两次。
  - **未出现过的聊天可先写**：收到第一条消息才生效；**不会**因此成为发送目标——发送目标仍只来自
    入站消息建立的别名表。
  - **`name` 不是真相源**：页面显示运行时别名，写盘时顺手存一份快照；名字过期不影响解析。
  - **白名单优先**：聊天不在 `allow` 里时门控覆盖不生效，也无害（以后加进白名单即自动接手）。
  - 结构化配置走专用页面（账号卡 → 设置：连接 / 白名单 / 会话三块），不进通用设置页（同 `providers.toml`）。
- **表达与克制（v1.0）**：默认把回复发到当前来源；模型可用标签控制表达——`<mention/>`（转 @）、
  `<quote/>`（转引用）、`<refuse/>`（本轮不发），发送前解析并剥除标签；只有要发到**别的会话**时才调用
  发送工具指定目标。参考 `astrbot_plugin_astrbot_enhance_mode` 的四件套：表达 / 拒绝 / 忽略某人 / 记忆检索。
- **群聊增强（v1.0 取这三样，源自 astrbot_enhance_mode）**：①群聊上下文注入发送者昵称 + 是否管理员标签；
  ②**输出标签**（模型写在回复里、发送前剥除）：`<mention/>` = 转成平台 @、`<quote/>` = 转成引用、
  `<refuse/>` = 本轮不发送；③按聊天设门控档位。v1.x 再考虑图片转述、跨群记忆检索、
  Bot 侧忽略某用户（ban）。
- **门控档位（每聊天一个，2026-11-01 定；存储见上面「平台配置结构」）**：
  - `only_trigger`（默认，群聊）：只有 @我 / 回复我 / `/#` 前缀才进对话；
  - `probability`：没被唤起的消息按概率决定是否插入对话（白名单内生效）；
  - `decision_batch`（2026-11-01 定，2026-11-11 定稿参数）：**合并多条再决策**——候选消息进该聊天的
    待判队列，**最后一条之后静默 2 s** 就判（期间每来一条重新计时），或**攒满 8 条立刻判**；
    **先到先判**，没有「≥N 条才攒」「达到 N 条顺延窗口」这类中间条件。判「说」→ 整批唤醒主模型一次；
    判「不说」→ 进节流等待。原 `decision` 档已删。
    - **不做回复后冷却**（2026-11-11 定）：角色刚说完话也照常走决策，接不接由决策模型自己判断
      ——要的是活人，不是被闸门掐住的话筒。节流只当**成本保险**，不承担行为约束。
    - 与平台合并（1.5 s / 8 条，见下）**共用同一个攒批器实现，但两组独立配置**：
      一个决定「合并成一次请求」，一个决定「合并成一次判定」，语义与失败处理都不同。
  - `always`（默认，私聊）：所有消息都进对话。
- **分段回复（v1.0 用规则，2026-11-01 定）**：按标点与长度在本地切分、带小延迟逐条发（零 token 成本）；
  模型分段（如 smart_segmentation 那样多调一次分段模型）留作 v1.x 候选，默认不开。
- **流式期间的新输入（2026-11-08 定）**：**排队 + 攒批**，不打断当前回复。
  - 前端（WebChat / GUI）：当前轮流式期间提交的输入默认进**队列**，等当前轮结束后按顺序处理；
    **不显示「已排队」文字**。队列放在输入框上方的**队列坞（QueueDock）**：折叠时显示「N 条待发送」，
    展开可编辑 / 删除；不做中途 steer（注入当前轮）——留 v1.x 再评估。
    参考 DeepSeek harness：`transcript / queued / steering` 三种 placement，队列条目不进对话流、
    单独停靠；AstrBot 的 `FollowUpTicket` 注入当前 run 的做法 v1 不采用。
  - 消息平台：同一**来源（聊天）**在 `batch_window`（默认 1.5 s）/ `batch_max`（默认 8 条）内到达的
    多条消息合并成一次模型请求；与决策模型的 `decision_batch` 复用同一套攒批器，但**不依赖决策模型开启**。
    **不同聊天不合并**——把 A 群和 B 群的消息混进一个请求，「本轮来源」就不存在了，
    发送工具的默认目标也会失去意义。
  - 语音（v1.x）：不即时打断；当前句说完再让出话轮；并支持对方持续说话时在**句子边界主动插话**
    （Neuro-sama 最新版本的表现），作为语音 turn-taking 的设计目标。
- **主管理员账户（v1.x，不做进 v1.0）**：设置一个 QQ 号 → 系统提示里注入「XXX 是你的管理员」；
  昵称撞名时额外提示「这不是你的管理员」。v1.0 只做 `admins_id` 的权限判定，不做人格化提示。

### 4.5 联网搜索

**现状（2026-11-06 核对）**：`behavior/search/` 已有引擎池（`bing` / `tavily` / `exa`）、归一化
`Result`、`EngineFailure`（带 provider / status / retry-after）、429 冷却、单次查询内每个引擎
只试一次；壳层 `tools/web_search.py` 统一渲染 markdown。实现细节见 `docs/forAiDoc/WEB-SEARCH.md`。

**v1 要改的**：把「固定三引擎 + `prefer_engine` 单值」换成 §3.5 的能力注册表（有序 + 可增删）。

| 字段 | 说明 |
|---|---|
| `id` | `bing` / `tavily` / `exa` / 用户新建的 `user-<slug>` |
| `kind` | `builtin` / `api`（Tavily 兼容协议）/ `mcp`（插件来源 v1.1） |
| `enabled` | 内置可禁用；`auto` 不可禁用 |
| 协议参数 | `api`：`base_url` + `api_key_env`（**只写环境变量名**，密钥仍在 `secrets.toml`）；`mcp`：`server` + `tool` |
| 可删除性 | 内置不可删；用户新建可删 |

- **顺序即 fallback 顺序**；`auto` 固定第一条（不可拖动、不可删），语义仍是「按查询语言分流」。
- **fallback 顺序页**：顶部输入框写顺序（`bing,tavily,exa,…`），下方列表可拖动，双向实时同步。
- **失败语义**：429 → 按 `retry-after` 冷却（缺省 60 s），冷却中的引擎直接跳过、不算失败；
  其它失败记 warning 后试下一个；**全失败返回错误 JSON**，不把异常抛给模型层。
- **Exa 特例**：走 MCP（`mcp.toml` 的 `[servers.exa]`）；MCP 未连接时该条显示「不可用 + 原因」，
  不参与 fallback，也不记成搜索失败。
- **落点（2026-11-11 定：方案 A）**：引擎注册表单独一个 `data/config/search_engines.toml`
  （`[[engines]]` 数组，**顺序 = 写盘顺序**），与 `providers.toml` 同性质——结构化、走专用「搜索顺序」页；
  `search.toml` 继续只放扁平键（超时 / 条数 / 截断），留在通用设置页。`prefer_engine` 随注册表退役。
- **批次**：随 **S7 统一连接**做（注册表 + 搜索顺序页）；见 §5.1、§6。
- **管理入口**：搜索页（WebUI）改顺序 / 启停 / 新建；也可以直接编辑上面那个 toml。
  **不为此单开 CLI 子命令**——改配置用编辑器就够（AGENTS §2）。
- **不做**：引擎健康度定时自检（频率与成本都没定）、结果缓存、跨会话搜索历史。

**规则（沿用）**：

- 内置 **Bing**：不可删除、可禁用；
- 内置 Tavily / Exa：现阶段**不可删除**（以后再考虑），可禁用；Tavily 无 key 时走 keyless 通道；
- 用户新建：只支持 **Tavily 兼容协议**的第三方端点 + MCP 来源；
- 插件提供：随插件启用出现、禁用后消失，不可单独删除（v1.1）。

### 4.6 TTS / STT / embedding 外联

- 三者都按能力注册表做「本地 / 外联」适配；密钥与端点进统一连接页。
- 与多模态的关系：模型能直接语音进出时，用户可选择绕过 TTS/STT；否则走原有链路。
- embedding 同时服务记忆与知识库；支持本地模型与外联接口。
- **移动设备默认禁止运行本地模型（2026-11-06 定）**：启动时集中探测一次运行平台
  （`infra/platform.py`；命中任一即视为移动设备：`sys.platform == "android"`、
  `sys.prefix` / `PREFIX` 含 `com.termux`、存在 `ANDROID_ROOT`）。命中后**所有本地推理一律关闭**：
  本地 embedding / 本地 STT / 本地 TTS / 将来的本地 LLM 全部不可选，只能走外联；
  设置页把「本地」选项置灰并写明原因。
  - 这不是「性能差一点的建议」，而是**依赖装不上**：OpenVINO / ONNX Runtime 的 aarch64 wheel 是
    glibc 构建（Termux 是 bionic），iOS / HarmonyOS 连 Python 运行时都没有。因此**不提供**
    「我知道风险，强制开启」的开关——开了也只会运行时报错。
  - 探测结果只作**能力闸门**，不写配置、不落盘（换机 / 换环境重算，符合「不把已验证状态存进库」）。
  - 不受影响：外联 embedding / 外联 LLM / `memory-lite`（SQLite + FTS5，不含模型）。
    移动端 v1 是瘦客户端（见 §4.7 末），本地不做推理。
  - 将来若真要在移动端跑本地模型（v1.x 以后），必须先有可用的 wheel 与实测机，再改这条闸门。
- **本地 embedding 的运行后端要可选（2026-11-01 定）**：现状写死 OpenVINO CPU 不礼貌——
  用户可能 CPU 不足而 GPU / NPU 有余。后端至少覆盖 ONNX Runtime / OpenVINO / CUDA(torch) 一类，
  按设备选；写死的只是「我们测试过的默认组合」，随 Aris 整体更新，用户可切换。
- **跨平台口径（2026-11-08 定）**：「多平台」先指**硬件后端**（CPU / GPU / NPU，ONNX / OpenVINO / CUDA），
  不是软件平台。**v1 只保证 Linux x86_64 的本地推理可用**；Windows / macOS 先保证「能装能跑外联」，
  本地推理随打包到 v1.1；v1.2 才是项目的基本完全体。移动端仍按上面的闸门禁用本地推理。
- **embedding 默认模型待实测（2026-11-08 定）**：候选 `hotchpotch/bekko-embedding-v1-a25m`（现默认，25M / 384 维 /
  MMTEB 57.5 / MIT）与 `ibm-granite/granite-embedding-97m-multilingual-r2`（97M / 384 维 /
  MTEB ML Retrieval 60.3 / Apache-2.0 / 32K 上下文）。S5 在同机做 A/B（中文真实查询 20~30 条，
  比 recall@5、单条延迟、常驻内存），胜者做默认、另一个保留可选；**不盲换**。两者维度同为 384，
  换默认不需要改表结构，但已建库仍按「库绑模型身份 + 影子表重建」处理。
- **PostgreSQL 不彻底写死（2026-11-01 定）**：内置便携版仍锁定并校验一个我们测试过的版本（随 Aris 更新），
  但允许指向**外部 PG**；外部与内置走同一套连接、迁移与备份口径。
- **首次启动不做任何初始化（2026-11-01 定）**：首次启动时既没有 LLM 连接、也没有 embedding
  （云端或本地）、也没有 memory / knowledge 库，所以**什么都不初始化**，全部**用到时才初始化**
  （建提供商 → 初始化连接；选 embedding → 初始化后端；建记忆库 / 知识库 → 建表）。
  用户真正创建这些时的**建议默认**（不是启动默认）：LLM 云端（我们只支持云）、embedding 云端、
  存储本地（PG / SQLite 视选择）。

### 4.7 记忆系统（memory / memory-lite）

**对外名称**：**APEMS**（`Aris Project Engram Memory System`，2026-11-03 定）——`Engram` 是名、
`Memory System` 是性质，全称只在 `MEMORY.md` §0 展开。只作对外文案（文档、发布说明、关于页）；
代码、CLI、配置与**界面导航**仍叫 `memory` /「记忆」（设置页 tab 就是「记忆」）。定位是
「经历在角色身上留下的痕迹」，不是检索工具。

**定位**：同一套记忆系统，两个存储后端；**工具面、内容语义、注入规则、权重/衰减、总结流程完全一致**，
只在存储与检索实现上不同。后端是**记忆库的属性**，不是全局配置。

| 后端 | 存储 | 检索 | 适用 |
|---|---|---|---|
| `memory`（full） | PostgreSQL + pgvector | 向量 + 关键词 | 常规/大规模 |
| `memory-lite` | SQLite（stdlib，零外部依赖） | **仅 FTS5 关键词**，**不做 embedding** | 低配设备（移动端 v1 是瘦客户端，见本节末） |

- **lite 不做向量**：需要语义检索就用 `memory convert` 转成 full（重建向量）；反向转换丢弃向量、文本不丢；
- **不做自动转换**：两个库后端不同也允许并存；给角色换库 = 换一份记忆（相当于换成别人的记忆），
  不换后端，角色系统不决定后端；
- **不默认初始化**：首次启动不建任何记忆表；创建角色时选择「不创建记忆 / 创建新记忆库（选后端）/
  使用已有记忆库」，**保存后才初始化**；无库时模块状态 = `uninitialized`（不是关闭、不是错误），
  允许“只想启动看看界面”的用户正常使用其余功能。**知识库同理**（见 §4.9）。
- **记忆库元信息 = 库自描述（2026-11-07 定）**：每库内部单行 `memory_library`（full 在该库 schema、
  lite 在 SQLite 文件内），不设全局注册表；`character.toml` 只存 `library_id`，物理位置
  （`mem_<id 前 12 位>` / `data/memory/libraries/<id>.sqlite`）由 id 推导；结构迁移逐库记在库内
  `memory_migrations`，不用全局 `store_schema_migrations`。契约见 `MEMORY.md` §1.1 / §10。
- **重要性在编码时定（2026-11-06 定）**：抽取时模型标「重要」（`importance ≥ 0.8`，可配）→ 直接进
  「重要」预设（`weight = 2048`、H = 73 天），**立刻常驻**；没标的中期（128 / 14 天）。
  **检索不改 `weight`**：真实命中只重置 `last_reinforced_at`、累加 `hit_count`（续命）；
  兜底检索与随机回忆连时钟都不重置。原「命中 +128 累加」已废——数值上它是中期到 512 的唯一路径，
  会让「被搜几次」压过「模型说重要」。
- **晋升（2026-11-06 调整）**：中期记忆在 30 天内被真实检索覆盖 **≥5 个不同自然日**（可配 5~7）→
  晋升长期（`weight` 256、H 73）；**止步于长期**，不会变成「重要」；自动随机回忆 / 兜底检索不计入。
  晋升写在命中那条写库路径里（一次性 `UPDATE`），不引入定时任务。细节见 `MEMORY.md` §1。
- **印象层（2026-11-06 定）**：新增 `facts` 事实表（一条 claim：主体 / 谓词 / 对象 / `confidence` /
  `source_kind` / 有效期 / `status`），**取代原 `relations`**——关系就是「对象是实体的 fact」，
  同一条信息只存一处；每条带 `evidence` 可回原文，`inferred` 默认不进常驻注入。
  人物卡 `[记忆·人物]` 由槽位段（facts 投影）+ 自由段（角色自述 ≤150 字）组成，取代原「关系摘要卡」；
  对话对象可能不止一个，按人各一张。事件加可选 `mood`（七档预设 + 允许自拟短词）。
  契约见 `MEMORY.md` §5 / §6.1。
- **大会话保留、大会话总结不做（2026-11-03 定）**：大会话（按消息时间戳聚类）用来**判断哪段时间在做事、
  哪段时间空着**，WebUI / CLI 提供时间轴查看；v1.0 暂不为它产出对话总结。
- **总结产物**：v1.0 只有 **compact 摘要** 与 **两周记**；小会话总结就是 compact，不另起一次调用。

**memory-lite 存储与检索规则**：

- 逻辑表与 full 一致（entries / sessions / messages / entities / facts），SQLite 方言：
  时间用 ISO8601 TEXT、JSON 用 TEXT、不建向量列；
- 提炼物与原文**分表**（避免大行拖慢页缓存）；
- 全文检索用 **FTS5 + trigram 分词**（中文 3 字切分，短词回退 LIKE）；排序 = BM25 + 权重 + 时间新鲜度；
- **不做全表计算排序**：注入查询先按时间/kind 过滤出小候选集再算 `w_eff`；列表页用 keyset 分页
  （`WHERE occurred_from < ?`），不用 OFFSET；
- pragma：WAL、`synchronous=NORMAL`、合理的 `cache_size`、`temp_store=MEMORY`；启动轻量 `ANALYZE`；
- 维护**事件驱动**：无后台调度器；衰减惰性计算（连续曲线，无台阶）；事件抽取挂在 compact 与跨日/阈值兜底；手机被杀也不丢数据。

**互转**：`aris memory convert --to memory|memory-lite`；中间格式 JSONL（每行一条记忆 + 来源 + 事实）；
先备份、后导入、向量重建；WebUI 红色确认。

**图 / 事实层（GraphRAG）**：full 与 lite **同一套实现**（2026-11-06 定）——`memory_entities` / `memory_facts` / `memory_event_entities`
都建、都维护；**不砍表、不砍查询，只砍递归 CTE**（v1 的图查询只有一跳，普通 JOIN 够用；多跳/社区摘要本来就不做）。
lite 没有向量 → 实体消歧退化为归一化 + `aliases` 精确匹配 + 人工合并，所以 `aliases` 是抽取硬要求。
人物卡是可选增强（`inject.people_card`，默认开、两个后端共用），有效槽位 <2 自动不渲染。
**归属（`is_owner`）可选**：同一 `cid` 至多一个、可以没有，只标「这个角色属于谁」，不参与
「当前发言人」判定；当前发言人由消息信封 `speaker` 经 `memory_identities` 解析。见 `MEMORY.md` §5.1 / §10。

**原文保留与检索（2026-11-08 定）**

- **原文全量保留并向量化**：`memory_sessions` / `memory_messages` / `memory_conversations` 存完整历史；
  原文另按语义边界切块、写 embedding（块表带 `embedding_model` 与分块 id）。摘要 / 事件 / 事实都是派生，
  删它们不动原文。
- **`raw` 检索 = 向量 + 关键词混合**：向量 ANN 取候选 + 关键词（`pg_trgm` / tsvector）取候选 → RRF 融合，
  返回块原文；**禁止裸 `LIKE '%词%'` 全表扫**。lite 走 FTS5 + trigram（§13）。
- **性能边界**：原文块按话轮切，工具超长输出可在切块时排除（原文仍保留，只是不向量化）；
  写入 embedding 成批做（挂 compact / 回合结束），不逐条调用。换 embedding 模型必须影子表全量重建。
- **检索参数可配但默认隐藏（2026-11-08 定）**：`memory.toml` 的 `[retrieval]` 暴露
  `rrf_k`（默认 60）、`weight_lambda`（默认 0.7）、`mmr_lambda`（默认 0.7）；设置页**默认不显示**，
  底部「高级检索参数」开关打开后才出现，点开关弹**风险提示**（调错会显著降低检索质量）。
  CLI 用 `aris config show memory` 可见；不把中间分做成用户可调项。

**角色笔记（2026-11-10 定）**

- **归属**：每角色（`cid`）一份，存 `data/characters/<cid>/notes.sqlite`（独立 SQLite，**不进记忆库**）：
  切 full / lite / 换库都不丢，随角色目录一起备份、一起软删除；不依赖记忆库是否已初始化。
- **形态**：一条笔记 = 可选标题 + 正文；增 / 读 / 改 / 删 + 模糊搜索。
- **检索**：SQLite **FTS5 + trigram**（中文 3 字切分，短词回退 LIKE），**不用向量**——向量是语义检索，两回事。
- **上限**：`memory.toml [notes]`，默认每角色 **500 条 / 单条 4000 字**；超限直接拒绝并提示，不静默截断。
- **工具**（记忆系统的**常驻工具**，不是 skill）：`memory_note_write(note_id?, title?, content)`（无 id 新建、
  有 id 更新）、`memory_note_read(note_id)`、`memory_note_search(query?, limit?)`（空 query = 按更新时间列最近）、
  `memory_note_delete(note_id)`。
- **v1 不自动注入**：只由模型按需调用；重要度 / 置顶 / 自动注入留 v1.x 再议。
- **入口**：WebUI 记忆页加「笔记」tab（列表 / 搜索 / 编辑 / 删除）；CLI `aris memory notes list|search|show|edit|remove`。
- 旧的 `src/aris/behavior/skills/note/` 是早期测试 skill，**v1 前删除**；它写的 `data/notes/` 先确认有无用户内容。

**人物卡重要度与防污染（2026-11-10 定）**

- **卡是派生的**：`memory_entities` 仍只表示身份（名字 / 别名 / 平台 id）；**有事实 或 有直接对话**才算有卡。
  纯提及只建身份、不建卡——人物页天然只有真正认识的人，路人不会污染列表、不会进前 15、不会占注入名额。
  「有没有卡」由查询现算，**不存字段**，所以不会漂移。
- **重要度**：`memory_entities.importance`（0~100 整数），**每张卡都有**；模型可标、用户可改。
  初始分按来源：主人 **80** / 有直接对话 **50** / 只有事实 **30**；`importance_source = default | model | user`
  只用于 UI 显示「谁设的」，**不做写入保护**——谁后改谁生效。
- **没有状态机**：不设 stub / active / archived。列表按重要度降序；低于阈值（默认 **20**，可配）折叠进「其他」组，
  可展开。这是**视图**，不是数据库状态；长期没互动分数自然低，就待在「其他」里，随时搜得到。
- **注入**：当前发言人完整卡 + 固定卡 ≤3 + 重要度前 3 的精简卡；总卡数 ≤6，按 `entity_id` 去重，顺序稳定保 KV cache。
  **主人保底前 3**：选卡时主人先占一个名额（卡有效才占；有效槽位 <2 仍按既有规则跳过）。
- **重要角色（前 15）**：只打「重要角色」标签，**不改变列表排序**；system prompt 给一份名字索引
  （名字 + 一句话标签），只在名单变化时刷新；`memory_find_person` 时前 15 加权。
  附加一条：抽取时人名能匹配前 15 的别名，**优先归并到那张卡**，减少裂卡。
- **人物卡全部可编辑**：印象、重要度、固定位、槽位事实都能改（用户 WebUI / CLI）；模型可改印象与重要度。
- **读工具**：新增 `memory_find_person(name, limit=5)`，返回 `entity_id` / 重要度 / 槽位 / 印象 / 最近互动；前 15 加权。
  这是补上「写完看不到、所以改不了」的闭环。
- **改事实工具**：新增 `memory_update_fact(fact_id, ...)`，**只改既有事实**（新事实仍只由抽取产生）；
  更正走「新行 + 旧行标 `superseded`」保留历史，返回新 `fact_id`；记 `updated_by = extraction | model | user`。
  防编造两条一起用：工具描述写「不确定就不要写」，注入的人物块注明「过往记录，可能过时，以对方当前所说为准」。
- **WebUI**：人物页默认显示有卡的实体，按重要度降序；「其他」折叠组放低分卡；可搜、可调重要度、可固定、可编辑事实 / 印象。

**移动端**：v1 **不做**；以后计划为**瘦客户端**（连远程/局域网后端做管理），iOS / HarmonyOS 现阶段明确拒绝。

**其余既有定案**：存储与 embedding 支持本地 / 外联；记忆按 cid 分区、角色互不串。
**内容模型与重审结论已并入 `docs/forAiDoc/MEMORY.md`**（2026-11-01 定稿）：由旧稿
（445 行，本机留档、不在仓库内）+ 2026-10-31/11-01 重审（M1–M65 + N1–N4 逐条结论）合成，**旧稿已丢弃、只保留新稿**，
作为唯一真相源（契约级，不含讨论过程；细节在 §6–§18）。

### 4.8 角色系统

**载体（2026-11-08 定）**：一个角色 = `data/characters/<cid>/` 目录，只保留两类文件：

| 文件 | 内容 | 谁写 |
|---|---|---|
| `prompt.md` | **完整人设 / 系统提示词正文**（单一文件，整段可编辑） | 前端 / CLI |
| `character.toml` | **配置**：`name`、记忆库绑定、`platform_ids`、LLM 提供商 / 模型绑定等 | 前端 / CLI |

- **不再有** `worldview.md` / `relations.md` / `growth.md`：世界观、人际关系、成长轨迹由**泛记忆系统**
  近似承担（`MEMORY.md` 的实体 / 事实 / 事件与人物卡），角色目录只回答「这个人是谁」。
  早期把它们做成三个只读 md 是冗余的，2026-11-08 推翻。
- `prompt.md` 只放人设正文；工具提示 / skills 菜单仍由 `BehaviorRuntime.system_prompt()` 在运行期追加，
  不写进文件。原文即最终 system prompt 的人设部分，所见即所得。
- **迁移（S10 一次）**：现有 `character.toml` 的四段人设 `intro / personality / tone / boundaries`
  加上三个 md 里的非空内容，按当前 `CharacterProfile.system_prompt()` 的顺序渲染成 `prompt.md`；
  `character.toml` 只留配置字段。新目录直接建 `prompt.md`。
- **示例对话（few-shot）**：v1 不做；v1.x 参考 AstrBot 的 `begin_dialogs`（人设 + 一组示例对白）再评估，
  避免 v1 又加一套结构化字段。

**cid（唯一标识）**

- 创建后**不可改**；改名 / 改人设只动文件内容，不动目录名；数据库只存 `cid`。
- 手动填写时校验（2026-11-08 定）：`^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$`，**允许大写、允许数字开头**；
  不得是 `.` / `..` / 保留名；**必须拒绝路径分隔符与 `..`**——现在 `CharacterStore.create(cid=...)`
  一个字符都不校验，S10 一开入口就是目录穿越（`cid="../../x"` 会写到 `data/` 外），**开入口前先补校验**。
  允许大写后必须做**大小写不敏感查重**：`Aris` / `aris` 在 macOS / Windows 会撞成同一个目录，
  创建时命中已有 cid（忽略大小写）直接拒绝；自动生成仍用 12 位小写十六进制
  （`uuid4().hex[:12]`，与现有 `fef3fc830e44` 同规格）。
- **去掉旧规则「不能以数字开头」**：十六进制首位约 62% 概率是数字，与自动生成冲突；
  `cid` 只当目录名与参数用，不当 TOML 键也不当 Python 标识符，没有理由排除数字开头。

**生命周期（S10 开工先补入口，2026-11-08 定）**

- **创建入口**：CLI + WebUI 都做。CLI `aris character new` **默认交互式**（逐项问名字 / 人设 / 记忆库策略 / cid），
  也允许参数化；参数化时支持 `--persona-file <path.md|.txt>` 导入设定。WebUI 创建页同样支持
  导入 `.md` / `.txt` 作为人设，避免只能手打长文本。
- **改名 / 改人设**：改名只动 `character.toml` 的 `name`；改人设只动 `prompt.md`。
- **列表 / 选定**：`character.list` / `character.resolve`；`cid` 该必填的地方一律显式传，
  防止静默串号（已有行为）。
- **删除（软删除）**：目录移到 `data/characters/.trash/<cid>-<时间戳>/`，**记忆库保留**；
  平台绑定立即清除；WebUI 可恢复或彻底删除。彻底删除时再单独确认「记忆库是否一并删除」，
  默认不删。

**平台绑定（2026-11-03 定）**

- `platform_ids` 存 `character.toml`（列表，**可空、可多个**）；平台实例侧同时记 `cid`，
  两侧双向校验，同一个实例不能出现在两个角色上。
- 未绑定实例的角色不会收到平台消息，但仍可从前端对话。

**默认角色**

- **只在首次启动播种**（从未创建过任何角色时，幂等）；用户删光后**不再自动复活**，
  角色列表空着并给创建引导。判断依据用持久标记（例如 `data/state/characters.json` 的
  `seeded = true`），不靠「目录是否为空」——否则删光就会重新播种。

**头像（v1.0 不做，整体推后到 v1.x；2026-11-11 定）**

- v1 只在 WebChat / 角色列表保留**展示位**（圆形占位），不做上传、裁剪、显示，也不读写头像文件。
- v1.x 实现时用 `data/characters/<cid>/avatar.<ext>`，随角色目录走；删角色时跟目录一起进 `.trash`，
  备份自然覆盖。将来 Live2D 可能部分取代头像，但文件仍留在角色目录。

**多角色同时运行（2026-11-08 定）**

- 每个角色**独立会话、独立串行队列**，文字消息可以同时处理；同一角色内仍严格串行、不并行改历史。
- **音频允许并发**：每个角色独立 TTS 队列 + 全局混音器，默认**不 ducking**、允许重叠
  （对齐 Neuro / Evil 会互相抢话的表现）；需要安静时可配强制串行，但 v1 默认并发。
- **角色间对话**：把对方的发言作为「对方说的话」**互相注入**彼此会话；记忆仍各存各的，不共享库。
- **每角色可绑自己的 LLM 提供商 / 模型**：`character.toml` 记绑定，未绑定用全局默认；
  会话级临时切换仍保留（§4.2）。

**多人格 = 多个人**：各自会话、各自记忆，互相当成不同的人；不做人格分裂。

### 4.9 知识库二期（2026-11-01 定稿）

**基准事实**

- **不默认初始化**：与记忆同一原则——首次启动不建表、不下载 embedding 模型；创建知识库 / 首次摄入时
  才初始化。无库状态 = `uninitialized`（不是关闭、不是错误）。理由：知识库**硬依赖 embedding**
  （本地模型要下载、外联要可用），启动即初始化会让只想跑起来看看的用户卡在下载/联网失败上。
- **知识库-lite 列为以后待办，v1 不做**：去掉 embedding 后的检索质量待验证，没有方案不立项。
- 存储 / embedding 走全局选择（本地或外联）。

**多库（「分组」= 多知识库，2026-11-01 定）**

- 新增 `knowledge_bases` 表（id / 名称 / 描述 / 创建时间 / doc_count / chunk_count /
  `meta jsonb NOT NULL DEFAULT '{}'`）；`knowledge_docs` / `knowledge_chunks` 加 `kb_id`（冗余存，单表可检索）。
  `meta` 是预留扩展位，v1 只建空对象、不读不写，将来要按库配置时不用改列。
- 旧数据迁移：现有单库数据自动归入「默认知识库」，首次启动迁移一次；新装用户无迁移。
- **检索范围**：工具参数 `kb` 可选，**不填 = 查全部库**；填库名 / id = 只查该库。
  工具描述里动态列出可用库名（库多时列前 N 个 + 总数）。
- 每库设置 v1 **全局一套**（embedding 模型、分块参数都走 `knowledge.toml`），不按库配；
  表里留 `meta jsonb`，将来要按库配再加列。
- WebUI：KB 管理页（新建 / 重命名 / 删除 / 切换当前库）+ 上传时选目标库 + 检索试验可选库。
- CLI：`aris knowledge kb list|new|rename|rm`、`add --kb <名称>`（CLI ≥ 前端）。

**PDF 摄入（2026-11-01 定，解析器 PyMuPDF）**

- 解析器 **PyMuPDF（fitz）**：快、文本质量好；它是 **AGPL**，与我们的 AGPL-3.0-or-later 兼容
  （这也是选 AGPL 的顺手收益之一）。
- **不做 OCR**：扫描件 / 纯图片 PDF 抽不到文字 → 文档标记 `no_text` 并在 UI 提示（不静默成功、不入库）；
- **不抽取内嵌图片**（v1 不做 media 表，图片理解留给多模态）；
- 分块：按页内段落聚合到 500–800 字符，chunk 保留**页码**，检索结果引用显示「文件 › 第 N 页」；
  md / html 沿用现有标题层级切法。
- 保留现有去重与幂等口径：文档级 content hash，同路径重复摄入 hash 未变跳过、变了软删重建。

**混合检索（2026-11-01 定）**

- 稀疏侧：**jieba 分词 + 自实现 BM25**（与 AstrBot 同路，可解释、参数可调）。
  - 新增 `knowledge_chunk_terms`（chunk_id, term, tf）与 `knowledge_terms`（term, df）两张表；
  - BM25 在 SQL 里算：`IDF = ln((N-df+0.5)/(df+0.5)+1)`、TF 饱和度用 `k1=1.5` / `b=0.75`；
  - 摄入时分词并写 terms（与向量化同一批事务）；删除 / 重建文档时同步清 terms。
- 稠密侧：现有 pgvector HNSW 余弦检索，top-k 候选（默认 50）。
- **融合 = 加权 RRF**（2026-11-01 定，不用 min-max 加权和）：
  `score = w_dense/(k+rank_dense) + w_sparse/(k+rank_sparse)`，默认 `k=60`、
  `w_dense=0.7` / `w_sparse=0.3`；最终取 top 5。
  结果里同时带原始 `dense_sim` 与 BM25 分数供调试与模型判断。
- **rerank 不做，留 v1.x**（2026-11-01 定）：成本是每个人都会关心的问题；`knowledge.toml`
  预留 `rerank.enabled=false` 与 provider 字段，v1 不实现。
- 结果格式沿用既有约定 `{"type": "knowledge_search_results", ...}`，新增 `kb` 与 `page` 字段。
- CLI 与 WebUI 都要有；agent 只给检索工具，摄入走 CLI/WebUI。

**上传与任务（2026-11-08 定）**

- 任务进度继续放内存（`webui/tasks._jobs`，`MAX_JOBS=20`），重启即丢；页面写清，**不做持久化**。
- 去重补一层 **content_hash 全局去重**：不同文件名但正文 hash 相同 → 直接 `skipped`，不重复算 embedding；
  同路径仍按 `source_path` + `content_hash` 幂等。

### 4.11 autorun（定时与主动任务）

> 2026-11-01 确认：autorun 要做（旧 D11「暂不做」作废）；旧 v1 方案只沿用 fallback 相关结论。
> 2026-11-01 定稿：单表 + cid、决策失败语义、允许 Aris 自建任务。

**形态**

- 宿主侧持久化任务表 + 调度器 + 到期投递会话，**不是常驻 cron daemon**。
  参考 AstrBot（APScheduler：`AsyncIOScheduler` / `CronTrigger` / `DateTrigger`）与
  DSH（漏跑只补最近一次、跨重启保留、普通消息投回原会话）。
- 调度器与 `serve` 同进程、复用主事件循环；任务表落 PG（owner `autorun`，走 `store/migrate.py`）。
- **单表 + `cid` 字段**，不按角色分表；`cid` 决定投递到哪个角色的会话，WebUI / CLI 按角色筛选。

**任务表（契约字段）**

| 列 | 说明 |
|---|---|
| `id` | 任务 id |
| `cid` | 归属角色 / 目标会话 |
| `name` | 显示名 |
| `kind` | `basic`（注册的 handler）｜`agent`（prompt 注入会话，走完整 agent loop） |
| `trigger_type` / `trigger_expr` | 见「触发」 |
| `timezone` | IANA 时区，任务级 |
| `payload` | jsonb：agent = `{prompt}`；basic = `{handler, args}` |
| `fallback_action` | 决策不可用时的不依赖决策的路径（可空），见「决策门控」 |
| `gate` | `never` / `auto` / `always`，见「决策门控」 |
| `enabled` / `run_once` | `once` 执行完自动 `enabled=false` |
| `status` | `idle` / `running` / `failed` / `expired` |
| `last_run_at` / `next_run_at` / `last_error` | 运行状态 |
| `created_by` | `webui` / `cli` / `agent` |
| `created_at` / `updated_at` | 时间一律存 UTC（`timestamptz`），展示按任务时区 |

**触发**

- `once`：ISO8601 时间点；`interval`：秒；`daily`：`HH:MM`；`weekly`：星期几 + `HH:MM`；
  `cron`：五段表达式。
- **cron 星期对外按标准 crontab 语义（0/7 = 周日）**，内部换算成 APScheduler 的「周一 = 0」——
  不换算会整体错一天，这条写进实现注意事项。
- 时区默认取全局配置（`autorun.toml`），任务级可覆盖。

**漏跑补偿**

- 启动 / 解冻 / 时钟跳变后重算 `next_run_at`，若已过期：
  - 周期性任务：**只补最近一次**，更早的丢弃并记日志（含丢弃条数）；
  - 一次性任务：补跑（闹钟不能吞），跑完置 `expired`。
- 补跑窗口 `catch_up_window`（默认 1 小时，可配）：超出窗口不补跑，只重算下次触发并记日志。
- 进程在任务执行中退出：重启后把遗留 `running` 视为中断，写 `last_error`，再按上面的漏跑规则处理。

**投递与串行**

- 到期不直接调模型，先进**该 cid 的会话串行队列**；排队超过 `max_delay`（默认 10 分钟）
  则丢弃并记日志。
- 投递形式：普通消息进会话历史（与 DSH 一致），带 `source=autorun` 标记供审计与 UI 区分，
  **不伪装成用户消息**。

**决策门控**

- `basic` 任务默认 `gate=never`：不经过决策模型，直接执行。
- `agent` 任务默认 `gate=auto`：到期先问决策模型（boolean，输入 = 任务上下文 + 最近对话摘要）
  → 要说话 / 做事才唤醒大模型；不要则只记审计与日志，**不消耗大模型**。
- `gate` 三档：`never`（跳过决策）｜`auto`（有决策模型就用，默认）｜`always`（必须决策，没有就失败）。
- **失败语义（2026-11-01 定，对齐 LLM fallback 纪律）**：
  1. **配了但调用失败**：可重试错误（429 / 5xx / 超时 / 网络）按退避**重试 1 次**；
     不可重试错误（鉴权 / 配额）不重试；仍失败进入第 3 步。
  2. **压根没配决策模型**：直接进入第 3 步。
  3. 第 3 步 = **任务声明的、不依赖决策的路径**（`fallback_action`：投递固定文案 / 调 basic handler）；
     没有声明则 **error 日志 + 本次不执行**，绝不静默降级成「总是说话 / 总是执行」。
- 决策判定为「不说话 / 不做事」是正常结果，不是失败。

**Aris 自建任务**

- 提供 agent 工具：`task_create` / `task_list` / `task_cancel`（`created_by=agent`）。
- 只能操作本 `cid` 下、由 agent 创建的任务；**不能创建 `basic` 任务**（basic 是内部 handler）。
- 每 `cid` 任务数上限（默认 50，可配），超限拒绝并回错误。

**任务页与 CLI**

- WebUI 侧栏「任务」：按角色筛选的列表（名称 / 类型 / 下次触发 / 上次结果 / 开关 / 创建者）
  + 立即执行 + 编辑 + 删除 + 最近错误。
- CLI：`aris autorun list|add|enable|disable|run|rm`（能力 ≥ 前端）。
- 任务执行失败：写 `last_error`、`status=failed`、记审计；**不自动重试**（避免失败任务反复刷屏与烧钱），
  下次仍按原计划触发。

**其他**

- 属于「影响数据的活动」：订阅 `system.freeze` 暂停调度、`system.thaw` 恢复并重算；
  冻结期间到期的按漏跑规则处理，与备份共用同一套冻结机制。
- 任务表随 `data/` 一起备份。

### 4.12 决策模型

- 新增能力：**决策模型**（decision provider），与 LLM 提供商同一套基础设施，但独立类型。
- 问题类型：boolean / choice / score；模型返回答案上的**概率分布**，不生成文本。
- 用途：**自主回复 / 自主操作的门控**——过去用小模型拼 system prompt + 近期事件 + 重要事件 + 最近对话
  输出 yes/no；现在交给决策模型，成本低、延迟低。
- 输入仍是组装好的上下文；输出结构化判定。
- **协议不是聊天补全**（已查官方文档，两个适配器都做）：
  - **TypeSafe System One**：`POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer`；
    体 `{ model, state, questions: { <id>: { type: noul|choice|score, instructions, criteria } } }`；
    响应 `{ model, answers: { <id>: … }, usage }`；另有 `GET /v1/models` 列模型；官方有 Python/JS SDK；
    **本地开权重模型（Jev-style 2B GGUF、H2O-Lightning-4B、pplx-decider-flash）经 wrapper 后讲同一 API**。
  - **OpenAI Decisions**：`POST https://api.openai.com/v1/decisions`，`Authorization: Bearer`；
    体 `{ model: "gpt-6-luna"（当前唯一支持）, input, questions: [{ type: predicate|choice|score, name, instructions }] }`；
    响应 `answers` 数组，按 `name` 对应；单请求最多 400 问；支持图片与 JSON 输入、prompt caching。
- **问题类型映射**（Aris 内部统一）：`bool → predicate / noul`、`Enum → choice`、`IntEnum → score`；
  适配器把两家响应归一成 `{ value, probabilities, confidence, score }`；其余 schema 类型直接拒绝、不发请求。
- **不调工具、不流式**：工具循环留在生成式主模型那边。
- **模式与默认（2026-11-03 定）**：`decision.mode = off | dedicated`，**默认 `off`**。
  **不做 `main_llm` 模式**：用主模型逐条判断的成本太高，宁可降级到概率 / 规则。
- **配置落点（2026-11-11 定）**：独立 `data/config/<cfid>/decision.toml`（**随档**），扁平键：
  `mode` / `provider_id` / `timeout_seconds` / `answer_threshold` / `confidence_threshold` /
  `history_size` / `batch_window` / `batch_max` / `min_interval` / `max_per_minute`。
  设置页单开「决策模型（实验）」tab（§3.3）：`mode` 常显，其余项 `condition` 于 `mode != off`。
  与 `chat.toml` 分开——并进聊天会让那个 tab 从 6 项变 16 项，语义也混（采样 vs 门控）。
  **按聊天的门控参数**（`gate` / `probability`）不在这里，在 `platforms.toml` 的 `[[chats]]`（§4.4）。
- **硬原则**：任何功能都**不得以「存在决策模型」为前提**；没有决策模型时按概率 / 规则降级，
  **只外接一个 LLM 也要能用 95% 以上功能**。
- **v1 适配面**：`dedicated` = **TypeSafe System One 适配器** + **OpenAI Decisions 适配器**（两个都做，可切换）。
- **置信度不足**：`confidence < 0.7`（可配）时按概率 / 规则降级（不做主模型复核）。
  参考实测：hosted Jev 约 200 ms/次、$20/百万次。
- **文档来源**（实现前复查）：`developers.openai.com/api/docs/guides/decisions`、`docs.typesafe.ai/api`；
  AG2 的 decision 实现可作字段对照参考，但**以官方文档为准**，不臆测字段。
- **门控频率（2026-11-01 定，2026-11-11 补边界）**：**不是每条消息都决策**。只在「没被唤醒、
  但处于候选状态」的消息上调用，并且做节流：同一聊天两次决策最小间隔（默认 5 s）、
  每聊天每分钟上限（默认 6 次）、只在白名单聊天里生效；已唤醒（@ / 回复 / 前缀）的消息直接进对话，不走决策。
  节流是**成本保险**，不是行为约束——不做「回复后冷却」，见 §4.4。
- **密集时攒批（2026-11-03 定，2026-11-11 定稿）**：消息密集时**不逐条判**，先攒一小批再一次性决策：
  **最后一条之后静默 2 s** 就判（期间每来一条重新计时），或**攒满 8 条立刻判**，先到先判。
  两个参数都可配；不再有「窗口内达到 N 条顺延一次」「最长等到 10 s」这类中间层
  （10 s 那一档在生态里对应的是「回复延迟」，不是决策窗口；见下）。
  判「说」→ 用整批消息唤醒主模型一次（仍走串行队列）；判「不说」→ 进入节流等待。
  依据：AstrBot 核心只有 0.1 概率、不攒批；enhance_mode 纯计数（`model_stack_size = 8`、无时间窗口）；
  angel_heart 用静默窗口（点名 1 s，新消息重计时）；group_chat 的 1~10 s 是**回复延迟**。
- **fallback（必须）**：没配置决策提供商、调用失败、超时（默认 2 s）时——**降级到「概率回复」**；
  概率也没配就降级到「仅触发」模式；降级只记日志，不弹错误、不阻塞消息处理。
- **决策输入（2026-11-11 定）**：**本聊天**的内存环形缓冲（最近 20 条，可配；**重启即丢、不入库**）
  + 当前来源标签 + 角色状态摘要（若有）；缓冲里把**本批消息标出来**。不读全局单会话的历史——
  单会话里混着别的平台的对话，用它判断「这个群现在该不该接话」等于瞎猜。
  缓冲在**白名单过滤 + 去重之后**记录，包含已唤醒的消息（否则决策模型看不到自己在回谁）。
  输出 boolean 概率，按阈值（默认 0.5）判定；不做文本生成、不进对话历史。
  参照：AstrBot 的 `group_chat_context`、enhance_mode 的按会话 300 条、angel_heart 的秘书模型，
  都是按聊天各存一份内存缓冲。

### 4.13 工具开关

- `ToolSpec.enabled` / `owner` 已在地基；v1 只做**按工具**的开关。
  **按 owner（整个插件）开关属于插件系统（v1.1），不在 `tools.toml` 里表达**——工具不该反过来管插件本身；
  模块级的「整块关」仍由 `modules.toml` 负责。
- **位置（2026-11-01 定）**：**不放设置页**，放侧栏的**「工具」折叠分组**下，三个平铺子项：
  **工具**（管理页）、**Skills**（管理页）、**MCP**（管理页）；配置本身**随档**
  （`data/config/tools.toml`，只记关闭项，缺失 = 全开）：

  ```toml
  # 只写被关掉的工具名；不写 = 全部启用
  [disabled]
  tools = ["web_search"]
  ```
- **管辖边界（2026-11-01 定）**：**工具管理页**只管**内置 + 插件**工具；**MCP 工具**的启停在
  **MCP 管理页**（连同 server 连接状态），不进 `tools.toml`——避免同一事实两处写。
- **默认全开**（2026-11-01 定）：目前没有执行命令 / 写文件的工具，联网类大多要用，不做默认关闭。
- **关掉的效果（2026-11-04 定）**：**移出模型工具面 + `tools.execute` 直接拒绝（记 warning）**；
  不做「只隐藏、仍可执行」的半开关。
- 模块关闭时其工具自然不出现；插件工具随插件启停；MCP 工具随 server 连接状态走。
- **「从属」要显示，但不写进配置（2026-11-04 定）**：工具页每行显示**提供方**（`behavior 内置` /
  `knowledge` / `mcp` / 插件名）。来源不需要另建机制——`ToolSpec.owner` 已存在，
  且 `register_declared_tools` 探询 `<模块名>.ai_tools` 时**天然知道是哪个服务声明的**
  （`declaration_failures` 已经在记 provider）。只需两件事：
  ① 探询时若 `spec.owner` 为空，用服务名前缀补上（内置工具由 behavior 显式填 `behavior`）；
  ② `aris tools list` 与工具页把它当**只读字段**展示。
  **`tools.toml` 里永远只有 `[disabled].tools`**——从属是事实，不是开关。
- 查证（同类产品惯例）：AstrBot / Dify / Coze / opencode 这类都把工具作为**能力页**而非设置项，
  列表 + 开关 + 详情；我们照此。

### 4.14 从 zip 导入 skills

**现状（2026-11-06 核对）**：只有**内置**技能，目录是包内 `behavior/skills/<name>/`
（`note` / `doc-coauthoring` / `frontend-design`）；**没有任何导入入口，也没有 `data/skills/`**
（`AGENTS.md` 里写的 `data/skills/` 目前是空的，`SKILLS_DIR` 指向包内）。本批把「内置」与「用户」
拆成两层。

**两个根**

| 根 | 内容 | 谁写 |
|---|---|---|
| 包内 `behavior/skills/` | 随包内置技能 | 只有我们 |
| `<data>/skills/` | 用户导入 / 自建技能 | 用户（CLI / WebUI） |

- 发现顺序：内置先、用户后。
- **同名不覆盖**：同名视为导入失败并报冲突；要更新先删再导。静默覆盖会让「我导入了一个技能」
  变成「我替换了一个内置技能」，而且内置技能是我们随包发的，用户无从判断被换掉了什么。
- 关掉单个技能：v1 **不做技能级开关**——不想用就不激活（内置技能的菜单项仍会出现在 system prompt，
  有一点 token 成本）；用户技能可以直接删目录。要不要加 `skills.toml` 的 `[disabled] skills`，
  作为 §7-31 的备选一起定（对称于 `tools.toml`）。

**zip 结构（只认两种，其余拒绝）**

1. 根目录直接是技能：`SKILL.md` + 可选 `tools.py` / `references/`；
2. 单一顶层目录：`<name>/SKILL.md` + …

多技能包、两层以上嵌套、没有 `SKILL.md` 的包一律拒绝。v1 不做批量导入。

**校验（导入前全过，一条不过就整体失败）**

- `SKILL.md` 必须有 frontmatter，`name` / `description` 非空；`name` 必须与目录名一致
  （不一致就拒绝——菜单名与目录名漂移会让 `activate_skill` 找不到目录）。
- 扩展名白名单：`.md` / `.txt` / `.py` / `.json` / `.toml` / `.yaml` / `.yml` / `.csv`；
  **拒绝**可执行文件、共享库、符号链接、绝对路径、`..`、`.` 开头的隐藏文件。
- 体积上限（2026-11-08 定）：做成 `skills.toml` 的 `[import]` 配置项，按三个维度设限——
  `max_total_mb`（默认 **10**）、`max_entries`（默认 **500**）、`max_file_mb`（默认 **2**）。
  必须按**解压后**算，不能只看压缩包大小（zip bomb 就是在压缩比上做文章）。
- **`tools.py` 会被 exec**：导入一个技能 = 允许它在 Aris 进程里跑任意代码，v1 **没有沙箱**。
  WebUI 必须显式警示并要管理员；CLI 要交互确认或 `--yes`。这条不能写成「已隔离」。

**落盘（原子）**

- 解压到 `<data>/skills/.tmp-<随机>/` → 校验 → `os.replace` 到 `<data>/skills/<name>/`；
- 任一步失败：删临时目录，目标目录**要么全新、要么完全没动**；不做「先删旧的再装新的」。
- 生效时机（2026-11-08 定）：导入 / 删除后标 `prompt_dirty`，**下一轮请求前重建 system prompt**
  （人设 + 工具提示 + 技能菜单），只付一次 cache miss，不要求重启；想要干净上下文用 `/#new-s`
  （见 §4.24）。不做「导入当下立即重建」——可能打断正在流式的轮次。

**入口**

- CLI：`aris skills import <zip> [--yes]`；列表 / 删除沿用现有 `skills.list` / `skills.delete` 服务。
- WebUI：技能页上传，冲突与失败原因逐条显示（不吞异常）。

**不做**：多技能批量导入、在线商店、远程 URL 导入、版本升级（v1 只支持删了再导）。

### 4.15 GUI 与打包

**框架：MyGO（Go）**——2026-11-03 定。理由（开发者原话归纳）：

- **前后端分进程**：GUI 用 Python 会跟后端搅在一个进程里，违背「GUI 只是前端」；
- 不要 Rust（Tauri 的代价），Tauri 相对臃肿；
- 引入 Go 可以接受：**工具链只存在于 `gui/`**，像 `webui/` 的 CSS/JS 构建那样隔离；
- MyGO 能出 deb / PKGBUILD，**但只作参考**：打包配方仍由我们自己写（重点在后端，发行层归我们）。

已核对的 MyGO 事实（v0.7.4，`egoist/mygo`，MIT，2026-09 建仓）：

- **Linux 用 GTK 3 + WebKitGTK 4.1**，不打包浏览器引擎；macOS 用 WKWebView、Windows 用 WebView2；
- **无 cgo**（purego dlopen），任何机器可交叉编译；
- `mygo build` 在 Linux 产出：可执行文件、`.desktop`、图标、`.tar.gz` + `install.sh`、`.deb`、`PKGBUILD`
  ——**只拿来对照**我们自己的配方，不直接发布它的产物（它的 deb 默认装 `/opt`，与我们「不用 `/opt`」冲突）；
- **我们不需要 Bun / Node**：只有「应用内嵌前端」才要 `frontendDist` + `buildCommand`；
  我们只加载后端给的 URL，所以 `gui/` 只需要 Go 一个工具链；
- **迭代很快**（v0.7.x，几乎每天一版）→ GUI 放 S13 最后做；**不锁死 MyGO 版本**，做的时候再评估 API 变化；
- 能力面（按官方文档）：`LoadURL`、单实例锁、托盘、通知、全局快捷键、深链、updater 插件
  ——**v1 用 `LoadURL` + 单实例锁 + 记住窗口尺寸 + 深链 `ariscore://`**；托盘 / 通知 / 全局快捷键 /
  自动更新留 v1.x。

**后端地址发现（2026-11-03 定）：连接信息文件，不是裸端口文件**

- 后端在 WebUI **成功 bind 之后**写 `<data>/state/webui.json`（原子写：tmp + rename）：
  `{ addr, pid, started_at, app_version }`；**正常退出时删除**，崩溃残留由读者判失效。
- 读序（GUI 与 CLI 共用同一套）：
  ① `--addr` 启动参数 → ② 环境变量 `ARIS_WEBUI_ADDR` → ③ `webui.json`（校验 pid 存活 + `/api/health` 握手）
  → ④ 探测 `webui.toml` 里的默认端口 → ⑤ 连接页（可手填，记住上次）。
- 为什么不是裸端口文件：要多带 `pid` 才能判「文件是上次崩溃留下的」；要带 `started_at` / `app_version`
  才能提示「你连的是旧版本后端」。业界同类本地服务（如 Jupyter 的 runtime 连接文件）也是这个思路。
- **GUI 有设置页**（2026-11-03 定）：后端地址（可填、可测连通）、启动时是否自动拉起后端、
  等待就绪超时、关闭窗口行为说明；GUI 自己的状态（窗口尺寸 / 上次地址）写 `<data>/state/gui.json`，随 `data/` 走。
- **关窗口只关 GUI，不停后端**（2026-11-03 定）：消息平台、autorun、记忆抽取继续跑；
  关窗前/关窗后给明确提示「后端仍在运行」，并提供**「关闭后端」按钮**。
- 「关闭后端」的实现：`POST /api/system/shutdown`（**需登录态 + CSRF**，走优雅停机，与重启同一条路径）；
  CLI 对等命令 `aris shutdown`（读连接文件 → 优先调该接口，失败退回对 pid 发 SIGTERM）。
  这是**前端路由**，不算「项目内部 HTTP 接口」（CMCB 的限制针对模块间通讯）。
- 形态：**同一安装包、两个程序**（2026-11-01 定）：
  - `arisp`：后端（Python，可独立运行；无 GUI 的机器也能单独装后端）；
  - `arisp-gui`：GUI（Go，半独立产品，代码在 `gui/`、有自己的 `go.mod`，**不 import 后端代码**，
    只认「后端 URL」这一个契约）。
  - **代码上几乎完全解耦**，只是**发行时捆在同一个安装包里**（装后端顺带装前端）。
- **GUI 启动行为（2026-11-01 定）**：启动后**自动在本机找已运行的 `aris`**（健康检查 / 端口探测）——
  找到就连；**没找到就在后台拉起一个后端**（包安装调 `arisp`，源码环境调 `aris`）并等待就绪再连接；
  都失败则显示连接页（地址可填、记住上次、重试）。后端仍可独立运行，GUI 只是前端。
- **版本号**：GUI **与主版本同步**（`1.0.0` 同号），用户少一个心智负担。
- **GUI v1 能力面**：单实例锁 + 记住窗口大小 / 位置 + 连接失败页 + **深链 `ariscore://`**；
  **托盘 / 通知 / 自动更新放 v1.x**（启动速度实测快，不需要靠托盘降低重启成本）。
- **深链（2026-11-08 定）**：scheme 用 **`ariscore://`**（与桌面 identifier / 包名一致，避开泛词 `aris`）；
  `.desktop` 注册 `MimeType=x-scheme-handler/ariscore;`，GUI 收到 URL 后跳对应页面
  （最小集：`ariscore://chat` 进聊天、`ariscore://` 进 Dashboard）。网页 / 外部程序靠它拉起 GUI。
- **启动速度**：MyGO 无公开冷启动基准；webview 路径主要取决于 GTK/WebKitGTK 初始化，
  原型出来后实测一次再定托盘是否提前。
- 打包平台（2026-11-01 定）：**v1.0 出 Arch 包 + deb（x86_64）**；AppImage / Windows / aarch64 / 交叉编译
  全部 **v1.1+**。开发者环境：Bedrock Linux（strata：arch / debian 13 trixie / gentoo / …，KDE Wayland，x86_64）——
  Arch 包本机实测，deb 在 Debian 13 stratum / 容器里验证。
- `.desktop`、图标、项目定义、品牌资源同批做。
- **打包路线 = 运行时 uv（2026-11-01 定 M1，2026-11-06 复核确认）**：包只装项目源码 + `uv.lock`
  + 启动器，**Python 解释器由 uv 在运行期安装**；保持「clone 下来即可运行」与安装版是同一条路径。
  选 M1 的理由：倒逼我们解决真实环境问题，不让打包把问题藏起来。
  - **解释器必须显式钉死**（仓库根 `.python-version`，当前 `3.14`），不能靠 `requires-python` 让 uv 自选：
    实测 `>=3.14` 会让 uv 装到 **3.15**，而 `pydantic-core` / `jiter` 等没有 cp315 轮子 → 转源码编译
    （要 Rust 工具链）。升级解释器 = 改 `.python-version` + `requires-python`，一次性动作。
  - 打包版首启执行 `uv sync --frozen --no-default-groups`：`dev` 与 `embedding` 两个默认组都不装
    （v1 的 embedding 默认云端，本地模型按用户选择再补）。
- **命名（2026-11-06 定）**：桌面 app-id **`dev.arisproject.ariscore`**；包名 **`ariscore`**
  （Arch 官方 / AUR / Debian / PyPI 均无占用）；桌面显示名 **`Aris Project`**（与 `branding.APP_NAME`
  一致——`aris` 比 `airi` 宽泛，不去掉 Project）。
  命令是**双名**：安装包上 PATH 用 **`arisp` / `arisp-gui`**（`aris` 已被 GNU Aris 的
  `bin_PROGRAMS = aris` 占用），**其余一律 `aris`**；`arisp` 只在「以包形式安装」的语境出现。
- **安装布局：不用 `/opt`**（2026-11-01 定）——FHS 里 `/opt` 是第三方自包含软件用的，需要 root 写、
  路径固定、与系统 python 隔离差。改为：
  - 源码 / `pyproject.toml` / `uv.lock` 放 **`/usr/share/ariscore/`**（发行包只读、架构无关）；
  - **deb 内置的 uv 与 GUI 二进制**放 **`/usr/lib/ariscore/`**（架构相关）；
  - **运行期 venv 放数据目录** `<data>/runtime/`（可重建，符合 `data/` 分层）；
    `UV_PROJECT_ENVIRONMENT` / `UV_PYTHON_INSTALL_DIR` / `UV_CACHE_DIR` 一律指到 `<data>/` 下，
    不污染 `~/.local/share/uv`；
  - `/usr/bin/arisp` 是 wrapper：首次运行 `uv sync --frozen --no-default-groups` 到 `<data>/runtime/`，
    之后用 `uv run --frozen --no-sync` 直接 exec 运行时；包升级后用版本戳比对重同步（细节留 S13）；
  - **uv 从哪来（2026-11-06 定）**：**Arch 包声明 `depends=('uv')`**（`extra` 有 0.13.7，滚动更新由用户承担）；
    **deb 内置一份钉死的 uv**——Debian 没有 uv 二进制包（sid 只有源码包，且只产 `python3-uv-build`，
    因为它的 Rust 依赖树没被 Debian 打包，不是许可证问题）。内置 uv 的版本与 sha256 记进
    `infra/components.py`，随包附 `LICENSE-MIT` + `LICENSE-APACHE` 全文（MIT / Apache-2.0 双许可，可随 AGPL 本体分发）。
    启动器统一「先找 `<prefix>/lib/ariscore/uv`，没有再用 PATH 里的 `uv`」；
  - GUI 二进制与 `.desktop`、图标随同包装；`mygo build` 只产 GUI 可执行文件（发行层由我们的脚本 / PKGBUILD 决定）。
- **Windows 必须兼容，但放 v1.1（2026-11-01 定）**：不能放弃 Windows 市场；GUI 走 MyGO + WebView2，
  后端走同一条运行时 uv 路径（`arisp.cmd` 包装器 + uv）；安装器用 MyGO 产出的 NSIS。
  v1.0 先把 Linux（Arch + deb）打通，架构上从第一天保证可移植。
- 单仓多构建单元：`src/aris/`（后端）、`webui/`（WebUI 与 GUI 共用的前端工作区，
  含 package.json 与 pnpm-lock）、`gui/`（Go 壳）、`docs/`（文档站）、`packaging/`（发行配方）。
- 构建隔离：普通 `uv sync` 不装 Node / 不构建 GUI；发版时 `ARIS_BUILD_GUI=1` 通过构建钩子打进发行物。
- 品牌：显示名与仓库 URL 只在 `branding.py`；`pyproject.toml` URL 与 `egg-info` 残留一并清理。
- **GUI 只是前端，不得脱离后端独立运行**：与音乐类客户端不同，Aris 去掉后端就是空壳。
  GUI 连不上后端时按上面的启动行为处理（自动找 → 后台拉起 → 仍失败给连接页与启动引导），
  不静默降级成"本地空壳"。
- **首启下载清单（2026-11-06 实测）**：发行物只带代码 + 启动器 + GUI，其余按需获取；
  全部落在 `data/` 下、可重建（分层见 `PORTABILITY-AND-SINGLE-SESSION.md`）。

  | 项 | 时机 | 大小（实测） |
  |---|---|---|
  | uv | 安装包（deb 内置；Arch 走系统包） | 16 MB 压缩 |
  | CPython 3.14（python-build-standalone） | 首启 | 73 MB |
  | 基础依赖（`--no-default-groups`） | 首启 | 装好 129 MB（含工程本体） |
  | 便携 PG + pgvector | 首启 | 约 40 MB |
  | 本地 embedding（torch / openvino + 模型） | 用户选「本地」时 | 1.5 GB+ |

  - 「本地 embedding 运行时未安装」不能裸抛 `ImportError`：`aris doctor` 要能检出、
    设置页给「安装本地模型运行时」、CLI 给对等命令（内部执行 `uv sync --frozen --group embedding`）。
  - **依赖升级到 CPython 3.15 的前置条件（2026-11-06 核实）**：`openvino` / `openvino-tokenizers`
    目前任何版本都没有 cp315 wheel（C++ 扩展，无法源码安装），`pyyaml` 也没有 cp315 wheel；
    其余依赖（numpy / lxml / pydantic-core / jiter / regex / markupsafe / torch / torchvision / tokenizers）
    已有可用的 cp315 或 abi3 轮子。等 OpenVINO 出新版本再一次性升级。

### 4.16 文档站（**v1.1**，2026-11-01 定）

> v1.0 范围已经很大，文档站整体推迟到 v1.1；v1.0 只保证 CHANGELOG 写清楚。

- **v1.1** 做；**VitePress**，放在 `docs/` 下。
- Node 依赖隔离：文档站与 `webui/` 同属仓库根的 pnpm workspace（根 `pnpm-workspace.yaml` +
  单一 `pnpm-lock.yaml`）；Node 文件不进 `src/aris/`，也不进 wheel。
  `.gitignore` 排除 `**/node_modules`、构建缓存。

### 4.17 i18n（2026-11-01 定稿）

- **语言**：`zh-CN` + `en` 双语，**en 完整翻译**（界面、CLI 帮助 / 提示 / 错误、后端错误消息）；
  **日志消息不翻**（见 §4.20）。
- **不翻的边界**：LLM 工具描述不翻（给模型看的，翻了反而破坏 prompt 稳定性）；日志消息不翻。
- **资源格式：JSON**（2026-11-01 定）——stdlib `json` 直接读、WebUI 注入方便、将来接翻译平台也方便。
  目录：`src/aris/locales/<locale>/<namespace>.json`，命名空间如 `common / nav / settings / errors / cli`；
  key 形如 `settings.chat.temperature.desc`（点分层级，禁止再嵌套语言层）。
- **后端**：`src/aris/i18n/` 提供 `t(key, **params)`；启动时按「当前语言」加载对应目录，缺失 key 回退
  `zh-CN` 并在 DEBUG 记一条（不静默丢文案）。
- **WebUI（Jinja SSR + Alpine）**：
  - Jinja 环境注入全局 `t()`：`{{ t("nav.dashboard") }}`；`<html lang="{{ lang }}">`；
  - 前端 JS 文案：渲染时注入 `window.__ARIS_I18N__`（只注入当前页用到的命名空间），
    toast / 确认框统一走 `window.t()`；
  - 配置项元数据：代码里声明 `desc_key` / `hint_key`，设置页用 `t()` 解析（AstrBot 同款思路）。
- **语言选择（2026-11-07 修订）**：配置项 `language = auto | zh-CN | en`，**随档**；优先级
  进程环境 `ARIS_LANGUAGE` > `settings.toml` > `auto`。`auto` 按 POSIX 顺序读
  `LC_ALL` → `LC_MESSAGES` → `LANG`，取第一个非空：`zh` 开头 → `zh-CN`，其它（含全未设置）→ `en`。
  **不做 `--lang`**，临时覆盖用 `ARIS_LANGUAGE=en aris ...`；WebUI 切换后重载页面生效。
  S1 的 en 只覆盖 CLI，WebUI 与配置项文案留 S14。
- **插件**：插件目录自带 `locales/`，SDK 提供 `ctx.t()`。
- **文档站**：VitePress 自带 locales（`docs/zh`、`docs/en`），不额外引框架。
- **格式与插值**：简单 `{name}` 插值（`str.format_map`）；缺参数保留占位并记 DEBUG。
  **v1 不做复数 / 性别**，不引 ICU；将来需要时再扩 `key.one` / `key.other` 约定。

### 4.19 破坏性更新迁移

- v1.0.0 之前不承诺旧配置 / 旧数据兼容。
- v1.0.0 之后的破坏性更新需提供「老版本 → 新版本」迁移，并在执行前征得用户同意。
- **备份恢复也要跨版本**（2026-11-01 定）：新版本必须能恢复旧版本的备份包，
  除非发布说明里**明确声明**「从 X 版本之前不再支持恢复」，否则默认支持。
- manifest 里有三个版本字段，**判定规则逐字段定（2026-11-01 定，唯一真相在此）**：

| 字段 | 情况 | 行为 |
|---|---|---|
| `format_version` | 未知 / 比当前新 | **拒绝**（没有对应解析器，读不了） |
| `format_version` | 更旧 | 允许，走逐代解析器（不写「只认最新」） |
| `db_schema_version` | 高于当前程序 | **拒绝**（旧程序开新库会坏） |
| `db_schema_version` | 缺失（早期备份） | 视为旧 schema，允许，恢复后跑迁移链 |
| `app_version` | 不同（升级或降级，含**比当前程序新**） | **警告 + 两次确认后允许**（A，2026-11-01 定） |
| 任意字段 | 低于发布说明声明的最低兼容版本 | **拒绝** |

- 旧库恢复后**自动跑新版本迁移**（迁移链本身就支持从旧 schema 往上走）；
- 恢复前快照 = 用户后悔时的退路。
- 迁移框架的形态（版本探测 / 迁移脚本 / 备份先行）在 v1 之后设计，本版只留接口位置。

### 4.20 日志与可观测（2026-11-01 定稿）

> 定方向：日志重点是**输出可读**，不是查询（查询与实时流由 `/logs` 页面承担，已存在）。

**语言（2026-11-01 定）**

- **日志消息直接写中文，不做 i18n**（与 AstrBot 一致：它的日志也只是中/英文字面量，只有 Dashboard UI 走 i18n）。
- 理由：单一语言利于 grep、避免切语言后历史日志混杂、195 处调用点不用全改 key；
  日志里保留**技术锚点**（错误码 / 路径 / 字段名），英文用户也能定位；真正的用户提示（CLI 帮助与错误）走 i18n。
- 若将来要英文日志，走「msg_key + 参数」方案（文件英文、WebUI 按语言渲染），属 v1.x。

**格式与输出**

- 格式：`[HH:mm:ss.SSS] [WARN][vX.Y.Z] [模块:行号] 消息`；短级别 `DBUG / INFO / WARN / ERRO`；
  版本标记只在 **≥ WARNING** 时带（便于用户报 bug 时对版本）。
- 三档可读性：默认 WARNING、`-v` INFO（阶段 / 回合摘要）、`-vv` DEBUG（请求摘要、重试原因、耗时）；
  运维类命令默认 INFO。
- 启动阶段化输出：一步一行（播种 → 迁移 → 自启 PG → embedding 预热 → WebUI 监听），带耗时与结果。
- 文件：沿用 `logs/YYYY-MM-DD/aris.log` + 10 MB 轮转 + 保留 30 天（可配）。

**实时流与查询**

- `/logs/stream` SSE 已存在；v1 只补：载荷加 `file` / `line` / `version`、内存环 200 → 500、
  前端按级别过滤、显示「模块:行号」。
- `/logs` 页面保留文件浏览 / 分页 / 下载。

**质量与排障**

- 噪音源压制：`httpx` / `httpcore` / `asyncio` / `aiosqlite` / `apscheduler` 等第三方 logger 压到 WARNING。
- 上下文 id：contextvar 注入 `session/turn/call/plugin` 短 id，行尾 `sid=…`，不要求每个调用点手写。
- 错误日志带**处置建议**：维护一张映射（401 → 查 `secrets.toml` 的哪个 key、连接拒绝 → `aris db start`、
  端口占用 → 改 `serve.toml`、embedding 模型缺失 → 首次启动会自动下载），并做敏感信息脱敏。
- 插件日志：宿主转发时加 `[Plug:id]` 前缀；**每插件级别覆盖**随插件系统再做。
- 重复告警做「首次 + 计数」收敛。
- **消息正文永不入日志**（只记长度 / 角色 / 来源 id），`-vv` 也只到摘要级。
- 审计与日志分工：审计保留结构化调用流水（服务 / 耗时 / 成败），日志负责人读，两边不重复打印。
- **审计不持久化（2026-11-08 定）**：只保留内存 `deque`，明确是**调试用**，重启即丢、不加表、不落盘、
  不做清理策略；页面写清「只反映本进程」。WebUI 侧栏**默认隐藏**审计入口，
  `webui.toml` 的 `show_audit = true` 才显示（`webui.show_audit` 进配置元数据）。

**明确不做**：OpenTelemetry trace、有界控制台 sink、日志消息 i18n（v1）。

### 4.21 上下文压缩（compact，2026-11-01 定）

- **触发方式可配**（`data/config/compact.toml`）：
  - `mode = "two_tier"`（默认）：`ctx > large_context_threshold` 时按 `large_context_target` 压缩；
    否则按 `small_context_ratio × ctx` 压缩。默认 `large_context_threshold = 236_000`、
    `large_context_target = 200_000`、`small_context_ratio = 0.85`。
  - `mode = "ratio"`：只按上下文占比决定，`ratio` 默认 0.85。
  - 任何比例上限 **0.95**，超过视为配置错误（不静默取默认）；
    两档模式下若 `small_context_ratio × large_context_threshold` 与 `large_context_target` 偏差 > 5%，保存时给 warning。
  - 触发阈值还要预留输出空间：实际阈值 = `min(配置阈值, 上下文上限 − 最大输出预留)`。
- **触发检查**：每轮请求前，用上一轮 provider 实测 usage + 本轮增量估算判断；被 provider 拒绝超长时按比例回退（85/70/50/35%）。
- **保留尾部原文**：默认 6 条（可配 0~20）。
- **小会话总结 = compact（2026-11-03 定）**：compact 产物就是小会话摘要，不另起一次总结调用；
  **大会话总结 v1.0 不做**（大会话定义与时间轴查看保留，见 §4.7），事件抽取挂在 compact 与跨日/阈值兜底上。
- **摘要调用**：独立一次 LLM 调用；成功才替换。失败语义见下方「compact 摘要 = 第二次调用」。
- **手动触发（2026-11-01 定）**：`/#new` 复用同一流程——① 事件总结写记忆 → ② compact 摘要；
  不是清空会话，也不是另写一套逻辑。**强制开新会话是 `/#new-s`**，两者语义不同，见 §4.24。
- **递归防护（必须）**：compact 摘要、事件总结、记忆抽取这类**维护调用**必须带 maintenance 标记，
  **跳过“请求前 compact 检查”**，否则总结调用自己会触发再次压缩（无限套娃）；
  维护调用也不计入轮次统计、不触发新的回合与 autorun。
- **重组顺序**：system + 记忆块 + 摘要 + 尾部原文 + 后续新消息（与既有定案一致）。

**事件抽取 = 第一次调用（2026-11-10 定）**

- **位置**：阈值触发 / `/#new` 时先 ① 事件抽取、再 ② compact 摘要；两次都在回复前（v1 阻塞）。
- **输入**：当前 history 去掉尾部 N 条——就是本次 compact 要吞掉的那段。**不从 DB 回读原文、不设水位线、
  不分块**（工具查实体表不算输入回读）；事件抽取不是两周记，只看当前上下文。
- **上次摘要**：若这段里含上一次的 compact 摘要，用明确分隔标出「这是你之前的摘要，只作前情，
  不要重复抽取」；尾部 N 条本轮不抽、不压，留在 history 里，下一轮再处理。
- **实现**：走标准 `AgentLoop`，**不是 one-shot**——DeepSeek 等 OpenAI 兼容 API 要求 `tool_calls` 后
  必须回传对应的 `tool` 结果（DeepSeek 还要带 `reasoning_content`，否则 400），不能跳过；因此工具执行后
  必然还有一次请求收尾。维护工具集 = `memory_find_person`（查重 / 对齐实体）+ `memory_write_events`
  （批量写缓冲）；`max_rounds` 默认 4；结束文本丢弃；缓冲在循环完整结束后一个事务提交，中途失败丢弃缓冲。
- **输出**：events + facts 由 `memory_write_events` 批量写入（可多次调用）；schema 见 `MEMORY.md` §9.5。
- **失败**：走正常 LLM 重试 / fallback 链；**全部失败就整轮失败**（不 compact、不回复），原文保留，
  下一轮重试；更复杂的回落留 v1.x。
- **大窗口保护**：单次事件条数上限默认 **60**（可配），提示里要求优先保留重要事件，超出丢弃并记日志，
  避免输出被截断导致 JSON 解析失败。
- **代价**：第一次阈值时输入可能很大（~236k）、输出长、耗时长；之后每次只处理上次 compact 之后
  尚未抽取的部分（加上被围栏的摘要），不会重复膨胀。

**compact 摘要 = 第二次调用（2026-11-10 定）**

- **位置**：① 事件抽取之后、回复之前（v1 阻塞）；`/#new` 同流程。
- **输入**：与 ① **同一段**（history 去掉尾部 N 条），**含上一次的 compact 摘要**——所以本质是**滚动合并**，
  不是「再摘要一次」。提示词按「合并重写」写：新对话优先，旧摘要里仍成立的保留，被纠正或不重要的可删
  （学 opencode 的 update 模式，专治滚动合并越滚越大）。
- **尾部保留**：按**对话消息**计 6 条（0~20 可配）。`history` 只含 `system / user / assistant 最终回答`，
  工具中间轮**不进 history**（`behavior/loop.py`：中间轮只在循环内存在），因此不会出现「tool 结果没有
  前驱 `tool_calls`」的 400，也不需要轮次对齐。
- **长度**：**不设数字上限**。学 opencode 用写法约束代替——短句、单行条目、不写大段、不嵌套列表、不写前言。
  撞到输出上限就接受，记 warning（截断的摘要也比砍掉整轮好；重试只会拖住回复）。
- **结构**：**不做模板校验**，五节缺了就缺了，接受并记 warning。
- **空输出 = 失败**（不能让摘要变成空，否则等于把历史清空）。
- **失败**：走正常 LLM 重试 / fallback 链；**全失败就整轮失败**（不 compact、不回复），下一轮重试；
  更平滑的回落（只压缩不抽取、标记待补等）留 v1.x。
- **重试幂等**：① 成功、② 失败会整轮重来，同一段会被抽第二遍。用确定性
  `extract_key = hash(cid, 区间首条 message_id, 末条 message_id)` 防重——重跑时**先删同 key 的抽取产物
  （且 `updated_by='extraction'`）、再写新的一批**，一个事务；即「直接覆盖上一次」。
- **摘要消息的角色**：**一条 `user` 消息**，开头 `[记忆·对话摘要]`，插在尾部原文之前；**不另加 assistant 确认**。
  理由：同角色连续不是协议限制（见 `API-CALL.md` §1.2），而概率回复下 `user` 连发本就是常态；
  标记让它与 `[记忆·关键]` 等注入块同语义——「系统给的记忆，不是对方说的话」（`MEMORY.md` §6.1）。
- **结构化、不自述**：摘要是给模型用的要素，不是给读者看的回忆录（`MEMORY.md` §9.2「叙事给人看，
  要素给模型用」）——条目式，用名字与绝对时间，不写「我 / 你」，不写前言。

**摘要提示词（学 AstrBot 的 Markdown 严格结构，内容改成 Aris；五节 = `MEMORY.md` §9.2 的统一要素）**：

```text
下面是你需要整理的材料。请把它们写成一份给模型续聊用的结构化记录。

## 输出格式
用 Markdown，按以下小节输出；没有内容的小节写“（无）”。每节一行一条。

### 这段时间发生了什么
- 

### 对方近况与状态
- 

### 约定与承诺
- 

### 关系与情绪变化
- 

### 未完成的事
- 

## 写法
- 用名字写「老张」「{角色名}」，不写「我 / 你 / 用户 / 对方」；
- 每条带绝对时间，格式 `2026-11-10 21:03`；
- 一行一条，短句；不写大段、不嵌套列表、不写前言；
- 只写事实与明确的情绪，不编造；不提及“压缩”“摘要过程”。

<之前的摘要>
{previous_summary}
</之前的摘要>

<之后的对话>
{new_dialogue}
</之后的对话>
```

- **合并要求**：第一次 compact 没有 `<之前的摘要>` 段，直接省略该段与这条要求；之后每次都有——
  新对话优先；旧摘要里仍然成立的内容保留，被新对话纠正、已经不再重要的删掉；只返回合并后的正文，
  不要复述这两段的原文。

### 4.23 关于页与彩蛋（2026-11-03 定）

**关于页**（WebUI / GUI 共用同一套前端）：

- 中间是项目图标；下面一排联系方式（B 站、X、GitHub 等），链接收在常量 / 资源表里，**不硬编码进业务逻辑**；
- 最后一个是**白色图标**：深色模式下也保持白色（不用 `currentColor`，用固定白 + 深色描边保证可见），
  点击触发彩蛋；图标本身不发散注意，靠颜色差被发现。

**彩蛋内容**：

- **默认**：播放**东方红一号卫星在轨播发的电子音版本**——1970-04-24 起从太空播出的那段
  纯电子旋律，**不是**李焕之的合唱编曲，也**不是**中央乐团灌录的唱片。
- **版权核查（2026-11-03 查证）**：分三层看，既不能用「民歌 = 无主」带过，也不能用
  「卫星 = 国家的」带过。

  | 层 | 权利人 / 状态 | 中国到期 | 美国到期 |
  |---|---|---|---|
  | 原词《移民歌》 | 李有源（1955 卒） | 2005 年底（已公有） | — |
  | 曲：陕北民歌《骑白马》调，1944 年《解放日报》发表的改编谱 | 改编者马可（1976 卒）、李增正（1977 卒，据传记资料） | 曲 **2026 / 2027 年底** | 约 **2039**（URAA 恢复） |
  | 1944 年改编词第二、三段 | 公木（1998 卒）、刘炽（1998 卒） | **2048 年底** | 同上 |
  | 1970 年卫星播发的电子音 | 录音制作者权 + 广播组织权，均按 50 年计 | 约 **2020 年底**（已过） | pre-1972 录音 **2067** |

  结论：
  - **电子音版本用不到李焕之的合唱编曲**（那层 2050 年到期，与本方案无关）；
  - 中国境内：录音与广播 2020 年底已过、曲的改编者最晚 2027 年底到期，
    **2028 年起该版本在中国境内基本无版权障碍**（编曲者身份不明的部分按 1970 年法人作品计，
    同样已过 50 年）——这是保守估计，不是法律意见；
  - 但 **GitHub 全球分发要算美国法**：词曲约到 2039、录音到 2067，**现在打包仍有风险**；
  - 「自己用合成器复刻一段」不豁免：那仍是使用这首曲。

- **版权之外还有四层合规（2026-11-04 补，这才是决定「外链」而不是「打包」的真正原因）**：

  | 层 | 说明 | 结论 |
  |---|---|---|
  | **软件许可** | 项目是 AGPL-3.0；打包进来的是**第三方权利资产**，AGPL 覆盖不到它，发行包会出现「整体权利不清晰」。Arch / Debian / AUR 对包内资产的许可证有硬要求 | 无法声明许可证的音频**不能进包** |
  | **平台内容政策** | 《东方红》是特定历史时期的标志性作品，国内应用市场 / 视频平台审核口径不一；GitHub 也受美国出口管制与 AUP 约束 | 由用户所在平台判定，不由我们承担 |
  | **链接方式** | 普通超链接不构成复制发行；但 **iframe 内嵌 / 直链音频文件 / 提供下载 / 镜像托管** 会把风险拉回「我们在传播」 | 只做普通超链接，新标签打开 |
  | **跨境分发** | GitHub 面向全球，美国法比中国晚（词曲 2039、pre-1972 录音 2067） | 中国境内合规不等于全球合规 |

  这几层不是法律意见，是「我们愿意承担多大风险」的判断。

- **因此 v1 的彩蛋 = 纯外链，不打包、不内嵌、不直链音频文件**（2026-11-04 定）：
  点击白色图标 → 新标签打开一个**普通超链接**（默认指向有授权的公开页面，地址收在数据文件里）；
  播放器、封面、版权信息都由目标站点负责。**「用户自备音频放 `data/easteregg/`」这条路也取消**——
  它会逼我们自己做播放器与格式探测，收益远小于复杂度，真想要的人直接点链接就行。
- **硬规则**：**包内不得出现任何《东方红》音频文件**（含衍生、重录、合成器复刻）。
- **特殊日期映射**：按日期把彩蛋换成别的内容，例如
  ENIAC 建成 → 百度百科；卡西尼号发射纪念 → 炙弹冰《卡西尼回旋于夜空》；103 机建成 → GeekLogic 复刻 103 机。
  映射表做成**数据文件**（可增删、可关闭），不写死在代码分支里。
- **失败必须静默**：链接缺失、外链打不开、日期表解析失败 → 不跳转，只记 debug 日志，**不影响任何正常功能**；
- 外链一律 `target="_blank" rel="noopener noreferrer"`；页面上**不出现音频元素**，用户点击前不发起任何网络请求。

### 4.24 会话生命周期与提示词重建（2026-11-08 定）

- **`/#new` 不是清空会话**：它是「上下文到阈值时的行为」——① 事件总结写记忆 → ② compact 摘要，
  **两次调用**，与自动 compact 同一套流程，不另写逻辑（§4.21）。
- **`/#new-s`**：强制开新会话（新 `session_id`），旧会话历史保留可查；用于 skills / 工具面 /
  模型发生变化后想要干净上下文，或不想被旧摘要影响时。与 `/#new` 分开，不合并语义。
- **提示词相关变更统一标脏**：skills 导入 / 删除、工具开关、每角色模型绑定、平台绑定等会改变
  system prompt 或工具面的操作，一律标 `prompt_dirty`；**下一轮请求前重建 `history[0]`**
  （人设 + 工具提示 + skills 菜单），只付一次 cache miss，不要求重启、不要求新会话。
- **工具开关的即时性**：工具定义每轮从 registry 现取，本来就立即生效；受影响的只是 system prompt
  里的工具提示 / 技能菜单，由同一条重建兜住。
- **重建失败**（如角色目录已被删除）：按「功能不可用 + error 日志」处理，不静默沿用旧 prompt。

## 9. 版本与发布节奏

### 9.1 渠道语义（单一数字线，预发布也占号）

| 渠道 | 定位 | 发布位置 | 测试范围 |
|---|---|---|---|
| **alpha** | 开发通道，长期存在 | `develop` 打 tag，不进 main | smoke：`import aris`、`aris --version`、`aris info`、**`aris serve --dry-run`**；**不跑 PG / embedding** |
| **beta** | 正式版前的候选版 | `release/vX.Y.Z → main` 标准流程 | 完整测试 **含 PG + embedding**，构建产物 |
| **正式版** | 稳定版 | main | 完整流程：完整测试 + 打包 + Release（文档站 v1.1） |

- 渠道只由 tag 前缀表达（`alpha-` / `beta-` / 无前缀）；版本串只写数字；
- 三个渠道共用一条数字线：alpha 用掉的号，beta / 正式版只能取更高号；
- 预留区间：`0.4.6`–`0.9.9`（含 `.x`）供跨越开发期消耗，`1.0.0` 为正式版。

### 9.2 版本与节奏

**版本 bump 规则（2026-11-01 定）**

- 小功能完成 → bump **patch**；中 / 大功能 → bump **minor**；
- **绝不把 `1.0.0` 消耗掉**：v1 开发期间只用 `0.4.6`–`0.9.9` 区间的号；
- **全部 v1 计划做完之后**才把版本 bump 到 `1.0.0`，走完整发版流程（`release/v1.0.0 → main` + tag + Release）。
- CHANGELOG 允许「v0.4.5 → v1.0.0 写巨量」——这是预期结果，不是问题；建议阶段累积写（不强制）。


- v1.0 期间每个 S 批次：按需发 alpha（develop 快照）；阶段末（S6 / S10 / S13 后）发 beta（候选，走 release 分支 → main）；
- 全部完成后 `v1.0.0` 正式版：`release/v1.0.0 → main` → tag `v1.0.0` → GitHub Release（含产物）；
- 发版前必须：`bash scripts/check.sh` 全绿、`release-check.sh` PASS、CHANGELOG 有对应段；
- **CD 在 v1.0 期间落地**：tag 触发构建、产物上传、Release 创建（文档站发布 → v1.1）；此后流程冻结。

## 11. 施工纪律（v1 期间）

- **实事求是，动手前先查文档（硬规则）**：不熟的技术、外部 API、第三方行为，一律先查**官方文档 /
  上游源码 / 本地实测**，再下结论、再写代码；查不到就标「未验证」并问开发者，
  **禁止凭印象编字段、端点、参数**（AGENTS §1）。同类产品（AstrBot / opencode / airi 等）只能当对照，
  不能当权威。v1 里最容易翻车的：**MyGO**（Go 框架，迭代极快，动手前重新读它的 README 与 release）、
  **Tailwind CSS v4 / daisyUI 5 / Alpine.js**（大版本 API 差异）、**OneBot v11**（反向 WS 握手头、
  消息段、`retcode`、`echo` 配对）、**PostgreSQL / pgvector / micromamba**（版本绑定与下载产物）、
  **uv 打包与运行时**、**TypeSafe System One / OpenAI Decisions**（决策模型协议）。
  能实测的以实测为准：`aris` CLI、`serve --dry-run`、最小请求探针，跑过才算数（AGENTS §7）。
- **做 WebUI 前先看开发者的结构图（硬规则）**：动手写任何页面、导航或布局前，先打开
  `docs/process/assets/webui-2026-11-01/` 的 7 张结构图（桌面全宽 / 折叠轨 / 手机 / 消息平台 /
  设置分类 / 设置页 / 工具开关），按图对骨架。图只定整体骨架，**图里没画的细节问开发者**，
  不自行发挥、不从图里猜（§4.1）。S2 出口验收逐项对图，不能只凭「页面能打开」。
- **每批次单独写施工文档**（2026-11-01 定，2026-11-03 改为 S 批次）：`docs/process/v1/Sx-<主题>.md`——任务 / 依赖 /
  验收 / 已知坑；开工前写、拍板后动工；阶段结束后移入 `docs/archive/`。
- **文档先行**：决策变更先改本文或施工文档，再写代码；未定项继续留在 §7。
- 每个 S 批次开 feature 分支（`feat/` `fix/` `refactor/`），小步提交，`--no-ff` 合回 develop；
  **允许并行**：不同阶段 / 模块各开分支，按 write scope 切分，Lead 汇总 diff 并跑全量测试。
- 阶段验收：§5 出口条件 + `bash scripts/check.sh` 全绿 + 相关集成测试 + 实跑 `serve`；结果写 `PROGRESS.md`。
- 提交格式、footer、changelog 规则按 AGENTS §8 / §9；CHANGELOG 建议每阶段往 `[Unreleased]` 追加。
- **版本节奏**（见 §9.2）：小功能 patch、中/大功能 minor；不消耗 `1.0.0`；每阶段末按需打 alpha tag。
- AI 不推送、不绕过推送限制；推送与发布由开发者执行。
- **发版必须问开发者（2026-11-01 定，硬规则）**：任何正式版 / beta / alpha 的发版动作（bump、tag、release、
  合并 main）前**必须先征得开发者明确同意**；AI **不得私自走发版流程**，只能准备到「待发」状态并汇报。
- 每阶段结束更新 `PROGRESS.md`（状态）与 `todolist.md`（勾选），契约变化写 `docs/forAiDoc/`。
